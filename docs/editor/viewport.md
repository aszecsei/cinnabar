# Viewport

How the host's frames reach a viewport through shared textures, the editor camera, the ID buffer and picking, selection, gizmos, snapping and a viewport's rendering settings, and how the editor shows the Game view and several scene views of one scene.

**In this document:** [Viewport](#viewport) · [Views](#views) · [Projection](#projection) · [View gizmo](#view-gizmo) · [Reflection probes](#reflection-probes) · [Navigation path](#navigation-path) · [Quality](#quality)

## Viewport

The editor shows the game in up to five viewports: four scene views and the Game view (see [Views](#views)). What follows is true of each, and says where it is a scene view's alone.

- **Frames:** the game renders each open viewport into the named shared textures `<prefix>.textureN` and signals `<prefix>.fence` (see [GPU](../gpu/presentation.md#presentation)).
- **One copy per frame.** Avalonia's Windows backend, ANGLE on D3D11, imports only D3D11 textures with a keyed mutex, in `R8G8B8A8_UNORM`, and it imports no semaphores. Its Vulkan backend imports only Vulkan's own handles. The `Direct3D12FenceNtHandle` semaphore type exists only for macOS. So the editor has its own D3D11 device, which opens the host's textures. On each composition update, if the host's fence shows a newer finished frame, the editor copies that frame into one of three keyed-mutex textures of its own, and gives that texture to the compositor. The fence is read on the CPU, so the copy never waits on the GPU.
- **Orientation:** the compositor takes an imported image's first row as its bottom one unless the import says otherwise, as OpenGL does. D3D's rows start at the top, so the editor imports its images with a top-left origin.
- **Opening the host's objects:** D3D11 cannot open a named shared object, so a D3D12 device on the same adapter turns the names into handles. D3D11 refuses a shared typeless texture from D3D12 unless it allows simultaneous access, so the shared textures have the typed sRGB format of the frame.
- **Same adapter:** shared objects open only on the adapter that created them. The first viewport control to attach reads the LUID of Avalonia's composition adapter, and the editor starts the host with `--adapter <luid>`. A session whose window moves to another adapter, and a viewport that finds an adapter other than the host's, report it in the console.
- **Back-pressure:** the editor reads a host texture only while it copies it. After each copy it ends a D3D11 event query, and when the GPU has passed it, the editor sends `Viewport_Acknowledged` with the viewport's number, the generation and the frame. The host renders frame k of a viewport into a shared texture only if k ≤ acknowledged + 2, so it never draws into a texture that the editor is still copying. Otherwise `core` gives the frame a scratch target that nothing reads. A slow editor drops frames from the viewport. It never stalls the simulation.
- **Attaching:** `ViewportControl` sets up its surface when it attaches to the visual tree, after it awaits the compositor's GPU interop. Each attach takes a ticket (`AttachTickets`), and a detach ends it, so a setup that resumes after a docking move detached and attached the control again builds nothing, and only the newest attach makes a surface. The compositor, the surface, the visual and the interop are one `Attachment`, which a detach disposes and lets go of.
- **Resizing:** the control shows its session at its size in physical pixels, once the size has not changed for 120 ms, so a drag makes one resize. The editor sends `Open_Viewport` with the new size. The game renders at that size from a following frame, clamped to `gpu.MAX_VIEWPORT_SIZE` on each side, and sends `Viewport_Target` with the new generation's name prefix, number and size. The editor opens the new set and releases the old one, and keeps the last picture on screen until the new generation's first frame. The game sends `Viewport_Target` for the first generation after `Open_Viewport`.
- **A fixed size:** automation can make the game draw a viewport at a size of its own (`EditorViewport.FixedSize`, which `viewport --set size=1920x1080` sets and `size=pane` clears; see [Automation](capture.md#automation)), so a measurement or a capture has the same size whatever the pane's. The editor then sends that size in `Open_Viewport` in place of the control's (`EditorViewport.DrawSize`), and the control fits the frame into itself, as it does any frame. The size is the editor's alone, and is not kept: a new editor draws every viewport at its pane's size.
- **Camera:** the editor owns each scene view's camera, `EditorCamera` in `Cinnabar.Editor.Tools`: a `World_Position`, a heading and a pitch, a vertical field of view of 60° and a near plane of 5 cm, with the far plane at infinity, or an orthographic projection (see [Projection](#projection)). It looks down its +z, with +y up, as the engine's views do. The editor sends it as `Editor_Camera` with the viewport's number when it changes and when the viewport opens, so a host restart keeps the view. While an editor is linked, the game draws an open scene view from its camera, in every mode. The Game view has no editor camera: the game draws it from its own (see [Views](#views)).
- **Camera controls:** in a scene view, the right button flies: the mouse looks, W, A, S and D move, Q and E go down and up, Shift is four times as fast, and the wheel changes the speed. Alt with the left button orbits about a pivot ahead of the camera, the middle button pans, and the wheel, or Alt with the right button, dollies toward the pivot. F frames the selection and puts the pivot on its middle, Frame Scene frames every entity, and opening a scene frames it. A click that selects leaves the pivot where it is. With Orbit Selection on, as Unreal's Orbit Camera Around Selection, Alt-orbit turns about the selection's middle instead, and the selection stays where it is on screen. The scheme is Unity's and Unreal's: the right button looks, and Alt with the left button orbits.
- **Views:** `render.View` is a pose and a projection. `render.view_projection` maps positions relative to the view, as render extraction gives them, to clip space, with reversed depth, `near / z` in perspective, so the depth test is Greater against a clear of 0. `render.view_depth` turns a depth back into a distance, for a perspective or an [orthographic](../rendering/frame.md#orthographic-views) view.
- **The ID buffer:** the renderer's world pass, the forward pass, writes a second target in `render.ID_FORMAT` (`R32_Uint`, which `editor.ID_FORMAT` names too): each pixel holds the index + 1 of the entity drawn there (`render.entity_id`), or 0, in its low 25 bits (`render.ID_ENTITY_BITS`, which `ecs.MAX_ENTITIES` fits), and the index of the mesh's submesh drawn there, at most 127, in the bits above them (`render.id_entity`, `render.id_submesh`). The cull pass carries the submesh in the draw record's `mesh` word, above the same bits. `editor.draw_frame` sets `keep_ids` for the scene views, and the pass keeps the IDs and its depth (see [Rendering](../rendering/frame.md#frame)). The renderer writes the IDs of the `Mesh_Renderer`s; a game that draws its own geometry in the world pass writes its IDs, and the sample puts each triangle's ID in its instance data.
- **Picking:** `Pick_Request` gives a rectangle of the frame in pixels; a click is one pixel. At a render scale below 1, the IDs and the depth are smaller than the frame, and the pick covers the scene's pixels under the rectangle (`scale_pick`, see [Rendering](../rendering/anti-aliasing.md#upscaling)). The editor's tools, which `editor.draw_frame` adds to each scene view as its overlay (`render.Frame_Overlay`), add a pass that clears a results buffer, runs a compute pass that sets a bit for each entity slot that the rectangle shows and reads the ID and depth at its corner, and copies the results to a readback buffer (see [GPU](../gpu/queues-streaming-readback.md#readback)). When the copy is on the CPU, a few frames later, `poll` sends `Pick_Result` with the entities in those slots, their scene IDs, and for one pixel the view-space distance and the submesh, or -1. A pick carries a ticket, so a frame that did not run it runs it again, and the game answers the picks in order. An entity slot can hold a newer entity by the time the answer arrives, which a click a few frames after a destroy can pick.
- **Selection and box selection:** in the viewport, a click selects what is under it, and a click on nothing clears the selection. A drag from empty space draws a box and selects what it shows. Shift adds and Ctrl toggles, as in the outliner. The editor sends `Set_Selection` with the entities' handles when the selection changes and after each snapshot, and the overlay pass, in the renderer's debug layer (see [Rendering](../rendering/layers-and-output.md#debug)), draws, while editing, an outline in the accent color where the selection's edge is, two pixels wide, around the selected entities and their descendants. The ID buffer has only what is visible, so where something is in front of the selection, the edge between them is the occluder's: the pass compares depths, and outlines only edges where the other side is behind the selection or is the background, so an occluder never looks selected. The view model is in front of every pixel of the world, whatever their depths, because it draws over the world (see [Rendering](../rendering/layers-and-output.md#view-model)): the pass reads the depth's stencil view for its bit, and compares depths only within the world or within the view model. A pick's depth uses the view model's near plane on its pixels. The hidden part of a selected entity has no outline.
- **Dropping materials:** a material or an instance dragged from the content browser over the viewport shows on the submesh under the mouse: the viewport picks the pixel under the drag, one pick at a time, and sets that submesh's slot of the entity's `Mesh_Renderer` (`materials.N`) in an undo entry that stays open, so the game draws it. Moving to another submesh puts the last one back, and so does leaving the viewport. The drop picks once more and keeps the slot that it finds as one undo entry. An entity that the editor locks, hides or did not load, one without a `Mesh_Renderer`, and a submesh past the 8 slots take nothing, and a drop there has a line in the console. Starting play puts back a material that a drag only shows.
- **Gizmos:** the gizmo's interaction is in C#. The editor knows the camera and the selected entities' poses from the document, does the hit test and the drag math, and makes field operations: a root's `Transform`, or a child's `Local_Transform` relative to its parent. The game only draws the gizmo from `Gizmo_State` (kind, pose, axes, size, the part under the mouse, and whether a drag holds it), over everything, in the same overlay pass. The editor sets the size so an axis is 110 frame pixels long. Move has arrows, plane squares and a square in the middle that moves in the view's plane; Rotate has a ring about each axis and an outer ring about the view's axis; Scale has an axis with a cube for each axis, and a cube in the middle that scales evenly. Only the near half of each rotation ring takes the mouse, and a plane seen edge on takes none.
- **Several entities:** a drag moves the selected entities that have no selected ancestor, about the primary entity: a move moves each by the same amount, a turn turns each about the primary entity, and a scale scales each and its distance from it along the gizmo's axes. Each step of a drag replaces the one before for each field, so a drag of any number of entities is one undo entry. Escape cancels a drag.
- **Tools and space:** Q, W, E and R pick Select, Move, Rotate and Scale, and N the [Navigation Path](#navigation-path) tool, while a scene view has focus, X switches between the world's axes and the entity's, F frames the selection, and H hides it. These keys belong to the viewport, so typing in a box never changes tools. The tools are also commands, on the ribbon's Home tab and in the tool palette. Select has no gizmo. Scale always uses the entity's axes.
- **Snapping** rounds a drag's change to 0.25 m, 15° or 0.1 of scale. The Snap command turns it on, and Ctrl during a drag does the opposite of the setting.
- **Mesh mode** (see [Mesh editing](mesh-editing.md#mesh-mode)) has keys of its own in the viewport: Tab enters it with the selected entities' mesh files and leaves it, a double click on a mesh enters it, 1, 2 and 3 pick vertices, edges and faces, `[` and `]` halve and double the grid, Escape clears the sub-selection and then leaves, and Delete and Ctrl+A act on the elements. A click, a box and the gizmo act on the elements, and the editor picks them itself, without the ID buffer. The Create tool makes the left button's drag a rectangle on the grid for the chosen primitive, and the Cut and Draw tools make clicks points, which Enter applies, Backspace drops one by one and Escape clears. Shift at the start of a Move drag of faces or edges extrudes them first, and the drag sets the distance, as it does after Extrude, Push/Pull, Offset, Inset, Outset and Bevel. With faces selected, the arrows shift their texture, `,` and `.` turn it and `-` and `=` scale it, by ten times the step with Shift and a tenth with Ctrl, and with Transform Texture on the gizmo drags the texture instead of the vertices (see [Mesh editing](mesh-editing.md#texture-tools)). A material dragged from the content browser shows on the face under it and drops onto it, or onto the selected faces when it is one of them. With Edit Pivot on, the Move gizmo stands on the mesh's entity and drags it with the geometry staying put, and Keep Planar makes a Move drag flatten the faces it would bend. The tool palette shows the element kinds while the mode is on, and the camera's speed line shows the grid's size.
- **Rendering:** the View tab's Rendering group picks what the settings viewport shows (see [Views](#views)), and the box at the top of each viewport picks that viewport's view: the lit scene or a debug view (see [Rendering](../rendering/post-processing.md#debug-views)), such as the lighting only, the albedo, the normals, the light complexity or the luminance, and for the reflections Roughness, Reflection Probes and Reflections. Its toggles turn temporal AA, bloom, the tone mapping, the fog, the clouds (see [Rendering](../rendering/clouds.md#clouds)), the ambient occlusion, the global illumination, the shadows, occlusion culling, the walk of the meshlets' hierarchy (see [GPU scene](../rendering/gpu-scene.md#mesh-shader-path)) and the game's post effects off in the viewport, and Brighter and Darker move its exposure by half a stop. Shading Stats, which is off until turned on, counts the forward pass's 2x2 quads for the Resource Monitor (see [Rendering](../rendering/lighting-and-shadows.md#quad-overdraw)). The Quality group draws the viewport at a quality in place of the game's (see [Quality](#quality)). The Helpers group shows the icons and the shapes of lights, volumes, reflection probes and cameras. These are the user's, not the scene's, so they do not change the game: the editor sends each open viewport's as `Set_Viewport_Settings` with its number when they change and when it opens, and keeps all four in `viewport.json` (see [Shell](shell-and-panels.md#shell)). `editor.draw_frame` applies each viewport's to that viewport's view. A screenshot that asks for debug views sends the captured viewport's this way too, and sends the user's settings again after (see [Capture](capture.md#screenshots)).
- **Helpers:** `editor.draw_helpers` draws, while editing, the shapes of lights, volumes, reflection probes and cameras as debug lines, for the selection or for every entity: a point light's range, a spot light's cones, a directional light's arrow, an area light's outline and normal, a volume's box or sphere with a fainter one at its blend distance, a reflection probe's boxes (see [Reflection probes](#reflection-probes)), and a camera's frustum. A selected navigation volume draws its navmeshes from the cooked blobs, each agent type in its color, and the Navigation Path tool's points draw the paths between them (see [Navigation path](#navigation-path)). A selected light's shape is in its color, and the others' grey. `editor.draw_frame` draws them before the frame. Hidden entities have none.
- **Icons:** lights, volumes, cameras and reflection probes have no mesh to click, so the viewport draws, while editing, an icon for each, 32 pixels across, facing the camera (`icons.hlsl`). A reflection probe's icon is a mirror ball that reflects the probe's own cube, at its sharpest mip, so it shows what the probe captured. Before the probe's first capture, or with the reflections off, the ball is grey. The icon pass runs before the pick, and writes the icon's entity ID and depth with its color, so a click or a box picks the entity and the selection outlines its icon, as for a mesh. A wall in front hides an icon. `editor.icon_instances` lists them, leaving out hidden entities.
- **The game's own window:** the viewport is always SDR, so Run Game (Ctrl+F5) opens the game in its own window, with the scene and content that it loads itself, to see the output mode, such as HDR. The Game Window group sets the project's output mode and quality preset, and this machine's (see [Architecture](../overview/architecture.md#project-settings)), which a running game takes at once. The window closes with the editor, and its output goes to the console.
- **New Volume** on the Home tab adds an entity with a Global `Volume`, for settings components (see [World](../world/volumes.md#volumes)). **New Reflection Probe** adds an entity with a `Reflection_Probe`, where the selected entity is (see [Reflection probes](#reflection-probes)).
- **Overlays:** the tool palette, the camera's speed with the tool and space, the box of a box selection, the [view gizmo](#view-gizmo) and the stats overlay are Avalonia controls over the viewport.
- **Input:** while the Game view has focus in Play, the editor sends keyboard, mouse, gamepad and text input, and the host gives it to the game as `core.Input` (see [Modes](document-and-scenes.md#modes) and [Core](../core/input.md#input)). The IME is on while the game has the input, and an overlay in the Game view shows what it composes ([Text and IME](../core/input.md#text-and-ime)). A scene view never sends input to the game.
- The editor does not reparent the host's window into its own. Windows attaches the input queues of a cross-process parent and child window, so a stall in the game would freeze the editor UI.

## Views

The editor shows the game in two kinds of view, in two documents of the dock layout that the user tabs, splits and closes: the Scene, which holds the scene views, and the Game, which holds the Game view (`EditorViewport` in `Cinnabar.Editor.Shell`, `SceneLayoutView` and `ViewportView` in `Cinnabar.Editor.Viewport`, `SceneViews.cs` and `EditorShell.Viewports.cs`).

- **A scene view** draws the world from the editor's camera, with the editor's tools, in every mode. It is where the user selects, moves and looks around, and it never sends input to the game.
- **The Game view** draws the world from the game's own camera, as a player sees it, with the game's UI and without the editor's tools. In Play it gives the game its keyboard, mouse, text and gamepads while it has the focus; in Edit it is passive. It has no tool palette, no camera controls and no picks, and it keeps the box at its top that picks its view. When the world has no entity with a `Camera`, the game draws its own default view (the sample's looks along +z from the origin), and the Game view shows a notice over it (`EditorShell.WorldHasCamera`, from the editor's mirror of the world, so it holds in every mode). Play brings the Game view to the front and gives it the focus (see [Modes](document-and-scenes.md#modes)).
- **A viewport is a number**, 0 to 4 (`link.MAX_VIEWPORTS`): 0 to 3 are the scene views, Perspective, Top, Front and Side, and 4 is the Game view (`EditorViewport.GameIndex`). Every viewport is the same on the wire: it has a shared target of its own, and every message about it names it. The shell makes all five once, so a view that closes and opens again keeps its camera and its settings.
- **Documents:** the Scene (`scene`) and the Game (`game`) are `ViewportDocument`s that the layout holds once each. The default layout has one document dock with the tabs Scene and Game, Scene in front. A document closes with its tab's button, either one, and then its dock may stay empty, and the game draws no view for it. Dragging a tab to the edge of the document area splits it, so the Scene and the Game can be side by side. A viewport document does not float. The View tab's Scene View and Game View show or hide each. The material, animation graph and UI editors' documents open in the dock that holds the Scene, or else the Game (see [Shell](shell-and-panels.md#shell)).
- **The Scene's views** are four toggles, one for each of Perspective, Top, Front and Side, on the View tab's Scene Views group (`EditorShell.SceneViews`, a `SceneViewSet` of flags, which `SetSceneViews` alone changes). A view that is on is in the Scene document, and one that is off is not drawn. At least one stays on: the last one's toggle is disabled. To see none, the user closes the Scene or brings the Game in front. A view that is on has its title over it, beside its view box, while it has company.
- **The arrangement** keeps the places of the quad, Perspective at the top left, Top at the top right, Front at the bottom left and Side at the bottom right, and collapses what is empty (`SceneGrid.Arrange`, which has no window in it): a row of one view spans the width, and an empty row or column is gone. Splitters sit between the rows and between the views of a split row, and a splitter that is in both rows moves them together. Their positions are not kept: a change of the views starts with equal tracks.

  | Views that are on | Arrangement |
  |---|---|
  | One | The view fills the document |
  | Two in one column of the quad: Perspective and Front, or Top and Side | Stacked, the one of the top row above |
  | Any other two: Perspective and Top, Front and Side, or the diagonals Perspective and Side, Top and Front | Side by side, the one of the left column on the left (Front is left of Top) |
  | Three | The two of a row side by side, and the third across the other row |
  | Four | The quad |

- **The presets** are shortcuts that set the toggles and nothing more: Single is Perspective alone, Two Side by Side is Perspective and Top, and Quad is all four. The Layout choice shows the preset that the toggles make, or Custom, which is not a choice. Nothing but the toggles is kept.
- **A change of the views** keeps every view that stays on in the document, and moves it to its cell, so its target stays and only its size can change; a view that goes off leaves the document, which closes it in the game, and one that comes on opens when its control has a size.
- **The views' cameras:** Perspective starts at the origin, looking along +z. Top, Front and Side start when they are first shown, from the Perspective view's camera: the same pivot at the same distance, so all four frame the same spot. Top looks down, a degree short of straight so that its heading means something, with +z up the view. Front looks along -z from +z, with +x to the left. Side looks along -x from +x, with +z to the right. Top, Front and Side are orthographic until the user chooses otherwise, and the first is a perspective camera (see [Projection](#projection)). A view that has moved keeps its place when it hides and shows again.
- **Visibility drives drawing.** A viewport is open in the game exactly while its `ViewportControl` is attached, visible and has a size. The control shows its session at its size (`ViewportSession.Presence`, `Shown` or `Hidden`, the one state that `Show` and `Hide` change), so a document that is behind another is hidden, as are the views that are off, a closed document and a window with no area. Only the views that are on show, and with the Game in front none of the four. The shell compares the presence with what the game was told (`EditorViewport.Opened`, which `SyncViewport` alone changes) and sends the difference:

  | The control | The editor sends | The game answers |
  |---|---|---|
  | Shows with a size | `Open_Viewport` with the number, the kind and the size, then for a scene view its `Editor_Camera`, and `Set_Viewport_Settings` | `Viewport_Target`, with the name prefix, generation and size of the shared target |
  | Shows with another size, once it settles | `Open_Viewport` with the new size | `Viewport_Target` with the next generation |
  | Copies a frame | `Viewport_Acknowledged` with the number, generation and frame | none |
  | Hides | `Close_Viewport`, and the editor lets go of the target | none |

  The game keeps what it has of a viewport only while the viewport is open, so a view that hides and shows again hears of its camera and settings again. A viewport that shows before the link, or while the host restarts, is opened when the link comes (see [Editor link](link.md#a-new-game-state)). Every view that opens hears of its camera, whether it started there or the user moved it.
- **The active scene view** is the one that the mouse is in, or last was. The tools act there: a click picks in its frame, the gizmo's hit test and drag use its camera, F frames the selection in it, and `EditorShell.Camera`, `FrameSize` and `ViewportSettings` are its own. The Game view is never the active one. A gizmo drag holds the active scene view until it ends, and a scene view that hides hands the role to the lowest one that is shown. The selection, the hidden entities, the tool, the space, snapping and mesh mode are the editor's, the same in every view.
- **The settings viewport** is the viewport that the View tab's Rendering, Quality and Helpers groups show and change: the one that the mouse or the keyboard last used, the Game view included. It is the active scene view until the user clicks into the Game view, and then the Game view, until a scene view is used again or the Game view hides. A thin frame in the accent color is around it while more than one viewport is shown. Each viewport's box at its top changes its own view without moving the role.
- **Each viewport has its own** view and features, exposure, icons and shapes, and quality (`Viewport_Settings`), kept in `viewport.json`. The Game view starts without icons and shapes, which are the editor's tools. The shapes are debug lines, which every viewport with a debug layer draws, so they are those of the scene view with the lowest number.
- **The gizmo and the box handles** are for scene views. Their size follows each view's camera and frame, so an axis is 110 frame pixels long in each, and the editor sends each open scene view its own `Gizmo_State` and `Box_Handles`, with the same pose and the same hot part. A pick is of the active scene view, in pixels of its frame, and a pick of a viewport that is not open answers with no hits, as does a pick of the Game view.
- **The game's size:** the Game view's size in physical pixels, or its fixed size, is the game's window size, which the game's UI and its camera's aspect follow. The editor sends `Game_Size` when that size changes, and again with a new game state if the Game view has had a size. The size stays when the Game view hides.
- **In Play** a scene view keeps the editor's camera and its controls, its selection and its picks, and shows the game from outside, while the Game view shows a frame in the mode's color and gives the game its input while it has the focus. The tools' overlays, the outline and the gizmo, are drawn only while editing, in every view. Paused gives the game no input.
- **A new game state** hears of every shown viewport again: its `Open_Viewport`, its `Editor_Camera` for a scene view, its `Set_Viewport_Settings`, its gizmo and handles, then the `Game_Size` and the `Capture_Source` (see [Editor link](link.md#a-new-game-state)). A viewport that is not shown is not opened.
- **Captures** read one viewport (see [Capture](capture.md#capture)): by default the scene view with the lowest number that is shown, which is the Perspective view while it is on, or else the Game view if it is shown. The editor tells the host with `Capture_Source` when that choice changes, and with a new game state; no viewport shown is -1, the host's own frame. A capture of a named viewport sends it for the capture's length and the default after. A capture with no viewport shown fails with the reason. The debug views of a screenshot change that viewport's settings and put them back, and the sidecar's camera and settings are its own.
- **Kept:** `viewport.json` has each viewport's settings, in the order of their numbers, which scene views are on (`Views`), and the projection that the user chose for each scene view (`Projections`). A file without them, or with the `Layout` of an earlier editor, has the Perspective view, or all four for Quad. A file from an editor with one viewport has one viewport's settings alone, which every viewport then starts from, with the Perspective view. `layout.json` has each document dock's documents and its active one (see [Shell](shell-and-panels.md#shell)).
- **Automation:** `editorctl viewport --viewport 2 --set shown=true` turns the Front view on and brings the Scene's tab to the front, and `shown=false` turns it off, which the last view that is on refuses, with the reason; the same holds for 0 to 3. `--viewport 4` shows or closes the Game document, and showing it puts the Game in front. `--set layout=Quad` sets a preset, one of Single, Two Side by Side (also written `TwoSideBySide`) and Quad. `--set projection=Orthographic` or `Perspective` sets a scene view's projection, and `--set view2d=true` makes it the 2D view, and `--set look=Top` turns it to look along an axis at once, one of Top, Bottom, Front, Back, Right and Left (see [View gizmo](#view-gizmo)). `--viewport <number>` makes `viewport`, `camera`, `screenshot` and `gif` act on that viewport (see [Capture](capture.md#automation)). The camera is a scene view's: the Game view has none.
- **What a view draws** is the renderer's (see [Rendering](../rendering/frame.md#views)): the game describes one frame and calls `editor.draw_frame`, and the editor package draws that frame in each open viewport as a view of its own, with the state of its own camera. The Game view is the frame's own view, with the game's camera, its hooks with the UI and the viewport's size, and each scene view an extra view, with the editor's camera, the game's hooks without the UI, and the tools as the view's overlay.

## Projection

Each scene view has a projection: `Perspective`, or `Orthographic`, which draws without perspective, as a plan, an elevation or a 2D scene is drawn (see [Rendering: Orthographic views](../rendering/frame.md#orthographic-views)).

- **The choice** is the View tab's Projection, for the scene view that the tab's settings are of, or the active one when that is the Game view, and each scene view's own [view gizmo](#view-gizmo) and menu. `EditorShell.SetProjection` is the one place that chooses it. `viewport.json` keeps it. Top, Front and Side are orthographic until the user chooses, and Perspective is a perspective camera.
- **A change of projection** keeps the pivot, and what is at the pivot as large on screen (`EditorCamera.SetProjection`): an orthographic camera shows the height that the perspective one showed at its pivot (`OrthographicHeight`), and a perspective one stands back to where it shows that height.
- **An orthographic camera** stands at least `OrthographicStandoff` (50 m) from its pivot, since it clips what is behind it, and sees `OrthographicFar` (10 km) ahead. The editor sends its projection, its height and its far plane in `Editor_Camera`.
- **Controls:** the wheel, or Alt with the right button, zooms: the camera shows less or more from where it is. The middle button pans, and so does the right button, since an orthographic view has no way to look around in. F frames the selection. Alt with the left button orbits, which makes the view a perspective one, as it has no axis any more. The choice stays, so the view is orthographic again the next time that it starts.
- **The 2D view:** the View tab's 2D View makes the scene view orthographic and looks along +z, with +x to the right and +y up, at the view's pivot (`EditorShell.Show2D`). This is how a 2D game's camera looks at its scene, so sprites lie flat in it. The Front view looks the other way, from +z, so it shows a 2D scene from behind.
- **The tools** work in both. A ray through a pixel is a `ViewRay`, an origin and a direction: from the camera in perspective, and from the pixel's point of the camera's plane along the view in orthographic (`EditorCamera.Ray`). The gizmo's drags, the mesh tools' picks and the point where a dropped prefab lands use it. A pixel is as large at every distance (`PixelSize`), so the gizmo and the handles are one size across the view. The pick's depth is along the view's axis in both.
- **In the game**, `editor.camera_view` gives the camera's `render.View` with its projection. The gizmo's lines face the way that an orthographic view looks (`gizmo_builder`). An orthographic scene view draws no fog: its camera stands back from what it shows by a distance that means nothing, and the fog between them would hide the scene.

## View gizmo

Each scene view has, in its top right corner, a gizmo of the world's axes as its camera sees them, and beside its view box at the top a menu of the same choices (`ViewGizmo` and `CameraTurn` in `Cinnabar.Editor.Tools`, `ViewGizmoControl` in `Cinnabar.Editor.Viewport`). The Game view has neither: it has the game's camera.

- **The gizmo** has a handle at each end of the x, y and z axes, in the gizmo's colors, red, green and blue: the positive ends large, with their letters, joined to the middle, and the negative ends small and pale. The handles turn with the camera, and those that point away are dimmer and drawn behind. A square in the middle is filled while the view is orthographic and an outline while it is perspective. Under it, the view's name and projection, such as `Top · Ortho` or `Free · Persp`: the axis that the camera looks along, within 1.5°, or Free.
- **A handle** turns the view to look from its end of the axis toward the pivot:

  | Handle | View | Looks along | Up the view |
  |---|---|---|---|
  | +y | Top | -y | +z |
  | -y | Bottom | +y | -z |
  | +z | Front | -z, with +x to the left | +y |
  | -z | Back | +z, as the 2D view | +y |
  | +x | Right | -x, with +z to the right | +y |
  | -x | Left | +x | +y |

  Top and Bottom are a degree short of straight, as the Top view starts (see [Views](#views)). The Top, Front and Side views start at Top, Front and Right.
- **The projection of a turn** is the one that the user chose for the view (see [Projection](#projection)), not the one that the camera has: a Top view that orbited, and so became a perspective one, is orthographic again when a handle turns it.
- **The turn** takes 200 ms, eased, about the pivot, with the heading the short way round, and what is at the pivot stays as large. A turn to perspective has it from the start, and a turn to orthographic switches at the end. Anything else that moves the camera, such as flying, a pan, the wheel or F, ends the turn where that move put the camera, and a view that hides ends its turn at once. A view that has not been shown yet starts first, from the first view's pivot (see [Views](#views)), so it turns about the same spot. `EditorShell.LookAlong` is the one place that starts a turn, and `EditorViewport.Turn` is its one state.
- **The middle and the label** switch the view between orthographic and perspective, which is the view's choice, as the View tab's Projection is (`EditorShell.ToggleProjection`).
- **The menu** at the top names the view as the label does, and has the six views and the two projections. Its choices act on that view.
- **The mouse:** only the left button acts on the gizmo, and makes its view the active one. A press that misses every part, the wheel and the other buttons go to the viewport, so the camera's controls work over the gizmo.

## Reflection probes

A [reflection probe](../rendering/lighting-and-shadows.md#reflection-probes) is placed, sized and captured in the viewport (`ProbeBoxes` in `Cinnabar.Editor.Tools`, `EditorShell.ReflectionProbes.cs`, `helpers.odin`, `icons.odin`).

- **Placing:** New Reflection Probe on the Home tab adds a probe where the selected entity is, with the default boxes, 5 m each way. The gizmo moves and turns it, as any entity.
- **The boxes:** the helpers draw a probe's boxes as the renderer takes them (`render.reflection_probe_extents` and `render.reflection_probe_blend`):
  - the influence box, in yellow when the probe is selected;
  - the fade, a fainter box inside it at `blend_distance`, when the fade is more than 0;
  - the projection box, in violet, when `box_projection` is on.

  An unselected probe's boxes are grey, and with the Selected helpers only the selection has them.
- **The handles:** when one probe is selected, outside mesh mode, each of its boxes has a handle on each face: the influence box's six, the fade's six, and with `box_projection` the projection box's six. The editor does the hit test and the drag, and sends the handles as `Box_Handles`, which the game draws as small cubes, 10 frame pixels wide, in the overlay pass, under the gizmo. The handle under the mouse is drawn in the gizmo's highlight.
- **A drag** of a handle moves its face, and the opposite face by the same amount, so the probe stays where it is and only its field changes:
  - an influence handle sets `extent`, and a projection handle `projection_extent`, each as the whole vector in the component's units, before the scale, with the defaults that the zeros stood for written out. A half size is at least 5 cm.
  - a fade handle sets `blend_distance`, in meters, from 0 to the smallest half size. It grows as the handle moves in.

  Snapping rounds the half size, or the fade, to its meters, and Ctrl does the opposite, as with the gizmo. A drag is one undo entry, and Escape cancels it.
- **Handles that would meet:** a fade of 0 would put the fade's handles on the influence box's, and so would a projection box that is the influence box. Such a handle stays two handles' widths from the influence box's handle, so each can be grabbed, and its drag starts from its value all the same.
- **The gizmo wins:** the tool's gizmo is drawn over the handles and takes the mouse first. With the Select tool, which has no gizmo, the handles take every click on them.
- **Capture:** the Properties panel's Capture button under the probe, and Capture All Probes in the Home tab's Scene group, ask the game to capture now (`Capture_Reflection_Probes`). A probe captures its six faces in one frame, whatever the quality's budget, and the frame that finishes it shows it, so the viewport and the probe's icon show the new capture at once. With several probes, one captures each frame. A probe that holds no slot is not captured (see [Rendering](../rendering/lighting-and-shadows.md#reflection-probes)). The commands need a linked game.
- **The probe's state:** the game sends a watched probe's state as `Reflection_Probe_View`, once after the watch, `None` included, then when it changes, and the world keeps it (`WorldModel.Probe`) until a `None`, the entity's destruction, a snapshot or the link's close. The Properties panel shows it (see [Shell](shell-and-panels.md#properties)).

## Navigation path

The Navigation Path tool shows the path that agents would take between two points of the scene, from the scene's cooked navmeshes ([AI: Navigation](../ai/navigation.md#drawing)).

- **Picking:** with the tool (the `tool.nav-path` command, N in a scene view, on the ribbon with the other tools), a click in a scene view picks a point on what is under it: the viewport picks the pixel and takes the point at its depth, as a drop does, without snapping it to the grid. The first click is the start and the second the goal. A third click starts again from it. A click selects nothing while the tool is on. Mesh mode has no such tool.
- **The game's side:** the editor sends the points as `Nav_Probe`, after each click and again for a new game state ([Editor link](link.md#a-new-game-state)). Leaving the tool sends none. The game keeps them in its `Session`.
- **Drawing:** in Edit, the helpers draw each point as a small sphere and, with both, the path between them for each agent type whose navmeshes are loaded, in that type's color, and faintly when the path is partial. A selected entity with a `Nav_Path` draws its own path, from where it stands to the goal. The navmeshes are the cooked blobs, so a change to the scene draws after the cook daemon cooks it.

## Quality

The View tab's Quality group draws the viewport at a [render quality](../rendering/quality.md#quality) in place of the game's, to see what a level costs and how it looks without changing the game's settings. The choices are the user's, in `Viewport_Settings` with the rest of the viewport's rendering.

| Choice | Values | What it replaces |
|---|---|---|
| Quality (`quality_preset`) | Game's, Low, Medium, High, Ultra | Every feature's technique and level, as `preset_quality` gives them |
| Anti-Aliasing (`anti_aliasing`) | Game's, Off, TAA, FXAA, SMAA, FSR | `Quality.aa` |
| Global Illumination (`global_illumination`) | Game's, Off, Screen Cascades, Split Cascades, Voxel Cones | `Quality.gi.technique`, at the preset's level or the game's (see [Rendering](../rendering/global-illumination.md#global-illumination)) |
| Render Scale (`render_scale`) | Game's, 100%, 75%, 67%, 50% | `Quality.render_scale`; 0 is the game's |
| Reflections (`reflections`) | Game's, Off, Probes, Screen Space, Ray Traced | `Quality.reflections.technique` (see [Rendering](../rendering/lighting-and-shadows.md#reflection-probes)) |
| Reflections Level (`reflections_level`) | Game's, Low, Medium, High, Ultra | `Quality.reflections.level`, which sets the probes' slots, their faces a frame and their size, and the rays' share of the pixels |

- **The game:** `editor.draw_frame` gives each view the quality of the game's frame (`Frame_Desc.quality`, or the renderer's) with the viewport's choices in place of its own, which `clamp_quality` limits to the device, so FSR is TAA where the device cannot run it, the split cascades are the screen cascades without `Ray_Query`, and so are the traced reflections the screen-space ones. A preset leaves the anti-aliasing and the render scale the game's, and sets the global illumination's and the reflections' techniques and levels with every feature, which the Global Illumination, Reflections and Reflections Level choices then replace, each on its own. A script or `editorctl` sets it as `globalIllumination`, for example `editorctl viewport --set globalIllumination=VoxelCones`.
- **Without an editor,** and with every choice the game's, the frame has the renderer's quality.
- **The game's own settings** are the Game Window group's (see [Architecture](../overview/architecture.md#project-settings)): the project's quality preset, or By Hardware, and this machine's in place of it. The group has only the preset; the reflections' and the global illumination's keys, such as `quality.reflections` and `quality.reflections.level`, are set in the files or by a game's settings menu. A preset in a file replaces the file's other quality keys, such as those that a game's settings menu saved, which show as Custom.
