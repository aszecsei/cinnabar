# Viewport

How the host's frames reach the viewport through shared textures, the editor camera, the ID buffer and picking, selection, gizmos, snapping and the viewport's rendering settings.

- **Frames:** the host renders into the named shared textures `<name>.textureN` and signals `<name>.fence` (see [GPU](../gpu/presentation.md#presentation)).
- **One copy per frame.** Avalonia's Windows backend, ANGLE on D3D11, imports only D3D11 textures with a keyed mutex, in `R8G8B8A8_UNORM`, and it imports no semaphores. Its Vulkan backend imports only Vulkan's own handles. The `Direct3D12FenceNtHandle` semaphore type exists only for macOS. So the editor has its own D3D11 device, which opens the host's textures. On each composition update, if the host's fence shows a newer finished frame, the editor copies that frame into one of three keyed-mutex textures of its own, and gives that texture to the compositor. The fence is read on the CPU, so the copy never waits on the GPU.
- **Orientation:** the compositor takes an imported image's first row as its bottom one unless the import says otherwise, as OpenGL does. D3D's rows start at the top, so the editor imports its images with a top-left origin.
- **Opening the host's objects:** D3D11 cannot open a named shared object, so a D3D12 device on the same adapter turns the names into handles. D3D11 refuses a shared typeless texture from D3D12 unless it allows simultaneous access, so the host's shared textures have the frame target's typed sRGB format.
- **Same adapter:** shared objects open only on the adapter that created them. The editor reads the LUID of Avalonia's composition adapter and starts the host with `--adapter <luid>`.
- **Back-pressure:** the editor reads a host texture only while it copies it. After each copy it ends a D3D11 event query, and when the GPU has passed it, the editor sends `Frame_Acknowledged` with the generation and the frame. The host renders frame k into a shared texture only if k ≤ acknowledged + 2, so it never draws into a texture that the editor is still copying. Otherwise `core` gives the frame a scratch target that nothing reads. A slow editor drops frames from the viewport. It never stalls the simulation. The host paces frames from the editor's `Hello` until the link closes.
- **Resizing:** the viewport sends its size in physical pixels, once it has not changed for 120 ms, so a drag makes one resize. The host renders at that size from a following frame, clamped to 8192 on each side, and sends `Frame_Target` with the new generation's name prefix, number and size. The editor opens the new set and releases the old one, and keeps the last picture on screen until the new generation's first frame. The host sends `Frame_Target` for the first generation right after the `Welcome`.
- **Camera:** in edit mode, the editor owns the camera, `EditorCamera` in `Cinnabar.Editor.Tools`: a `World_Position`, a heading and a pitch, a vertical field of view of 60° and a near plane of 5 cm, with the far plane at infinity. It looks down its +z, with +y up, as the engine's views do. The editor sends it as `Editor_Camera` when it changes and when the link connects, so a host restart keeps the view. While an editor is linked, the game draws from it (`editor.view`); without one, the game draws from its own camera. In play mode, the game's camera is used, unless the editor turns on its free camera (see [Modes](document-and-scenes.md#modes)).
- **Camera controls:** the right button flies: the mouse looks, W, A, S and D move, Q and E go down and up, Shift is four times as fast, and the wheel changes the speed. Alt with the left button orbits about a pivot ahead of the camera, the middle button pans, and the wheel, or Alt with the right button, dollies toward the pivot. F frames the selection and puts the pivot on its middle, Frame Scene frames every entity, and opening a scene frames it. A click that selects leaves the pivot where it is. With Orbit Selection on, as Unreal's Orbit Camera Around Selection, Alt-orbit turns about the selection's middle instead, and the selection stays where it is on screen. The scheme is Unity's and Unreal's: the right button looks, and Alt with the left button orbits.
- **Views:** `render.View` is a pose and a projection. `render.view_projection` maps positions relative to the view, as render extraction gives them, to clip space, with reversed depth `near / z`, so the depth test is Greater against a clear of 0. `render.view_depth` turns a depth back into a distance.
- **The ID buffer:** the renderer's world pass, the forward pass, writes a second target in `render.ID_FORMAT` (`R32_Uint`, which `editor.ID_FORMAT` names too): each pixel holds the index + 1 of the entity drawn there (`render.entity_id`), or 0, in its low 25 bits (`render.ID_ENTITY_BITS`, which `ecs.MAX_ENTITIES` fits), and the index of the mesh's submesh drawn there, at most 127, in the bits above them (`render.id_entity`, `render.id_submesh`). The cull pass carries the submesh in the draw record's `mesh` word, above the same bits. While an editor is linked, the game sets `keep_ids` and the pass keeps the IDs and its depth (see [Rendering](../rendering/frame.md#frame)). The renderer writes the IDs of the `Mesh_Renderer`s; a game that draws its own geometry in the world pass writes its IDs, and the sample puts each triangle's ID in its instance data.
- **Picking:** `Pick_Request` gives a rectangle of the frame in pixels; a click is one pixel. At a render scale below 1, the IDs and the depth are smaller than the frame, and the pick covers the scene's pixels under the rectangle (`scale_pick`, see [Rendering](../rendering/anti-aliasing.md#upscaling)). `editor.add_viewport_passes` clears a results buffer, runs a compute pass that sets a bit for each entity slot that the rectangle shows and reads the ID and depth at its corner, and copies the results to a readback buffer (see [GPU](../gpu/queues-streaming-readback.md#readback)). When the copy is on the CPU, a few frames later, `poll` sends `Pick_Result` with the entities in those slots, their scene IDs, and for one pixel the view-space distance and the submesh, or -1. A pick carries a ticket, so a frame that did not run it runs it again, and the game answers the picks in order. An entity slot can hold a newer entity by the time the answer arrives, which a click a few frames after a destroy can pick.
- **Selection and box selection:** in the viewport, a click selects what is under it, and a click on nothing clears the selection. A drag from empty space draws a box and selects what it shows. Shift adds and Ctrl toggles, as in the outliner. The editor sends `Set_Selection` with the entities' handles when the selection changes and after each snapshot, and the overlay pass, in the renderer's debug layer (see [Rendering](../rendering/layers-and-output.md#debug)), draws, while editing, an outline in the accent color where the selection's edge is, two pixels wide, around the selected entities and their descendants. The ID buffer has only what is visible, so where something is in front of the selection, the edge between them is the occluder's: the pass compares depths, and outlines only edges where the other side is behind the selection or is the background, so an occluder never looks selected. The view model is in front of every pixel of the world, whatever their depths, because it draws over the world (see [Rendering](../rendering/layers-and-output.md#view-model)): the pass reads the depth's stencil view for its bit, and compares depths only within the world or within the view model. A pick's depth uses the view model's near plane on its pixels. The hidden part of a selected entity has no outline.
- **Dropping materials:** a material or an instance dragged from the content browser over the viewport shows on the submesh under the mouse: the viewport picks the pixel under the drag, one pick at a time, and sets that submesh's slot of the entity's `Mesh_Renderer` (`materials.N`) in an undo entry that stays open, so the game draws it. Moving to another submesh puts the last one back, and so does leaving the viewport. The drop picks once more and keeps the slot that it finds as one undo entry. An entity that the editor locks, hides or did not load, one without a `Mesh_Renderer`, and a submesh past the 8 slots take nothing, and a drop there has a line in the console. Starting play puts back a material that a drag only shows.
- **Gizmos:** the gizmo's interaction is in C#. The editor knows the camera and the selected entities' poses from the document, does the hit test and the drag math, and makes field operations: a root's `Transform`, or a child's `Local_Transform` relative to its parent. The game only draws the gizmo from `Gizmo_State` (kind, pose, axes, size, the part under the mouse, and whether a drag holds it), over everything, in the same overlay pass. The editor sets the size so an axis is 110 frame pixels long. Move has arrows, plane squares and a square in the middle that moves in the view's plane; Rotate has a ring about each axis and an outer ring about the view's axis; Scale has an axis with a cube for each axis, and a cube in the middle that scales evenly. Only the near half of each rotation ring takes the mouse, and a plane seen edge on takes none.
- **Several entities:** a drag moves the selected entities that have no selected ancestor, about the primary entity: a move moves each by the same amount, a turn turns each about the primary entity, and a scale scales each and its distance from it along the gizmo's axes. Each step of a drag replaces the one before for each field, so a drag of any number of entities is one undo entry. Escape cancels a drag.
- **Tools and space:** Q, W, E and R pick Select, Move, Rotate and Scale while the viewport has focus, X switches between the world's axes and the entity's, F frames the selection, and H hides it. These keys belong to the viewport, so typing in a box never changes tools. The tools are also commands, on the ribbon's Home tab and in the tool palette. Select has no gizmo. Scale always uses the entity's axes.
- **Snapping** rounds a drag's change to 0.25 m, 15° or 0.1 of scale. The Snap command turns it on, and Ctrl during a drag does the opposite of the setting.
- **Mesh mode** (see [Mesh editing](mesh-editing.md#mesh-mode)) has keys of its own in the viewport: Tab enters it with the selected entities' mesh files and leaves it, a double click on a mesh enters it, 1, 2 and 3 pick vertices, edges and faces, `[` and `]` halve and double the grid, Escape clears the sub-selection and then leaves, and Delete and Ctrl+A act on the elements. A click, a box and the gizmo act on the elements, and the editor picks them itself, without the ID buffer. The Create tool makes the left button's drag a rectangle on the grid for the chosen primitive, and the Cut and Draw tools make clicks points, which Enter applies, Backspace drops one by one and Escape clears. Shift at the start of a Move drag of faces or edges extrudes them first, and the drag sets the distance, as it does after Extrude, Push/Pull, Offset, Inset, Outset and Bevel. With faces selected, the arrows shift their texture, `,` and `.` turn it and `-` and `=` scale it, by ten times the step with Shift and a tenth with Ctrl, and with Transform Texture on the gizmo drags the texture instead of the vertices (see [Mesh editing](mesh-editing.md#texture-tools)). A material dragged from the content browser shows on the face under it and drops onto it, or onto the selected faces when it is one of them. With Edit Pivot on, the Move gizmo stands on the mesh's entity and drags it with the geometry staying put, and Keep Planar makes a Move drag flatten the faces it would bend. The tool palette shows the element kinds while the mode is on, and the camera's speed line shows the grid's size.
- **Rendering:** the View tab's Rendering group picks what the viewport shows: the lit scene or a debug view (see [Rendering](../rendering/post-processing.md#debug-views)), such as the lighting only, the albedo, the normals, the light complexity or the luminance. Its toggles turn temporal AA, bloom, the tone mapping, the fog, the ambient occlusion, the global illumination, the shadows, occlusion culling, the walk of the meshlets' hierarchy (see [GPU scene](../rendering/gpu-scene.md#mesh-shader-path)) and the game's post effects off in the viewport, and Brighter and Darker move its exposure by half a stop. The Quality group draws the viewport at a quality in place of the game's (see [Quality](#quality)). The Helpers group shows the icons and the shapes of lights, volumes and cameras. These are the user's, not the scene's, so they do not change the game: the editor sends them as `Viewport_Settings` when they change and when the link connects, and keeps them in `viewport.json` (see [Shell](shell-and-panels.md#shell)). The game passes them to its frame with `editor.render_overrides` while an editor is linked. A screenshot that asks for debug views sends them this way too, and sends the user's settings again after (see [Capture](capture.md#screenshots)).
- **Helpers:** `editor.draw_helpers` draws, while editing, the shapes of lights, volumes and cameras as debug lines, for the selection or for every entity: a point light's range, a spot light's cones, a directional light's arrow, an area light's outline and normal, a volume's box or sphere with a fainter one at its blend distance, and a camera's frustum. A selected light's shape is in its color, and the others' grey. The game calls it before it draws the frame. Hidden entities have none.
- **Icons:** lights, volumes and cameras have no mesh to click, so the viewport draws, while editing, an icon for each, 32 pixels across, facing the camera (`icons.hlsl`). The icon pass runs before the pick, and writes the icon's entity ID and depth with its color, so a click or a box picks the entity and the selection outlines its icon, as for a mesh. A wall in front hides an icon. `editor.icon_instances` lists them, leaving out hidden entities.
- **The game's own window:** the viewport is always SDR, so Run Game (Ctrl+F5) opens the game in its own window, with the scene and content that it loads itself, to see the output mode, such as HDR. The Game Window group sets the project's output mode and quality preset, and this machine's (see [Architecture](../overview/architecture.md#project-settings)), which a running game takes at once. The window closes with the editor, and its output goes to the console.
- **New Volume** on the Home tab adds an entity with a Global `Volume`, for settings components (see [World](../world/volumes.md#volumes)).
- **Overlays:** the tool palette, the camera's speed with the tool and space, the box of a box selection and the stats overlay are Avalonia controls over the viewport.
- **Input:** while the viewport has focus in play mode, the editor sends keyboard and mouse input, and the host gives it to the game as `core.Input` (see [Modes](document-and-scenes.md#modes) and [Core](../core/input.md#input)).
- The editor does not reparent the host's window into its own. Windows attaches the input queues of a cross-process parent and child window, so a stall in the game would freeze the editor UI.

## Quality

The View tab's Quality group draws the viewport at a [render quality](../rendering/quality.md#quality) in place of the game's, to see what a level costs and how it looks without changing the game's settings. The choices are the user's, in `Viewport_Settings` with the rest of the viewport's rendering.

| Choice | Values | What it replaces |
|---|---|---|
| Quality (`quality_preset`) | Game's, Low, Medium, High, Ultra | Every feature's technique and level, as `preset_quality` gives them |
| Anti-Aliasing (`anti_aliasing`) | Game's, Off, TAA, FXAA, SMAA, FSR | `Quality.aa` |
| Render Scale (`render_scale`) | Game's, 100%, 75%, 67%, 50% | `Quality.render_scale`; 0 is the game's |

- **The game** gives them to its frame as `Frame_Desc.quality`, from `editor.viewport_quality(&editor, &renderer)`: the renderer's quality with the viewport's choices in place of its own, which `clamp_quality` limits to the device, so FSR is TAA where the device cannot run it. A preset leaves the anti-aliasing and the render scale the game's.
- **Without an editor,** and with every choice the game's, the frame has the renderer's quality.
- **The game's own settings** are the Game Window group's (see [Architecture](../overview/architecture.md#project-settings)): the project's quality preset, or By Hardware, and this machine's in place of it. A preset in a file replaces the file's other quality keys, such as those that a game's settings menu saved, which show as Custom.
