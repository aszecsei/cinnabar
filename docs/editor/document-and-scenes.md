# Document and scenes

The editor owns the scene: edits are operations with inverses, the host's world mirrors the document, and the scene file is text with stable IDs. This document covers the document model, the modes, several open scenes, and the scene format and loader.

**In this document:** [Document model](#document-model) · [Several scenes](#several-scenes) · [Scenes](#scenes)

## Document model

**The editor owns the scene.** The host's world is a mirror of the editor's document while the editor is in edit mode.

- **Why:** the host can lose its world at any time. A crash loses it, and so does a soft restart after a `Game_State` layout change (see [Hot reload](../overview/hot-reload.md#reload-sequence)). Unsaved edits must survive both. If the host owned the scene, they would not.
- **Edits are operations.** Every change is an operation on the document: create or destroy an entity, rename, reparent, set active, add or remove a component, set or reset a field, remove a behaviour, and set or reset a behaviour's field. Each operation returns its inverse when it applies. The editor applies an operation to its document, puts it on the undo stack and sends it to the host in `Apply_Operations`. The host applies it to its world. The editor never waits for the host to confirm an edit.
- **Resetting** a field removes it from the scene, so a component's field is zero and a behaviour's field has its class's default, as in a scene that does not set it.
- **Edits of more than one operation:** destroying an entity destroys its descendants first, each with its own operation, so undo creates each after its parent. Duplicating copies an entity and its descendants with new scene IDs, and a reference inside the copy refers to the copy. Reparenting sets the entity's `Local_Transform`, or for a new root its `Transform`, so it stays where it is in the world: `SceneEdits` composes poses as the engine's propagation does.
- **Transactions:** an interaction groups its operations into one undo entry. A gizmo drag or a drag on a number field sends field values while it moves, and makes one undo entry when the mouse is released. A step that replaces the step before it, such as the next value of the same field, takes its place, so the entry has the last value and the first inverse. An operation that does not fit the document, such as one for an entity that is not there, undoes the transaction's earlier steps and goes to the console.
- **Open edits:** one undo entry is open at a time. Each interaction that opens one gets a token (`SceneEdit`) from `EditorShell.TryBeginEdit`: a gizmo drag, a distance tool such as Extrude, a material or prefab drop over the viewport, and a drag of a field in Properties, the Face panel or the atmosphere view. It previews, commits and cancels through the token, and the shell's `OpenEdit` names the owner. A token whose entry has ended does nothing, so an owner cannot end another's entry. While an entry is open, another drag does not start, and a one-shot edit is refused with a console line that names the owner; the open entry stays. The mesh tools first commit a distance tool that waits, as its owner does. Play ends the open entry: a scrub commits as it is, and a gizmo drag, a distance tool or a drop that only shows its result is put back. Opening a scene cancels it. Either way, the owner learns that its entry ended, and its drag stops. Save does not end it: Save waits until the entry ends (see Save below).
- **Undo and redo** are Ctrl+Z and Ctrl+Y. An entry that an edit-mode behaviour made follows the entry before it: undo, redo and a move in the history take the two together, and the host gets their operations in one `Apply_Operations` (see [Behaviours' edits](#behaviours-edits)). A new edit after an undo drops the entries after it. The document is dirty when its position in the history is not the one that the file has, so undoing back to it makes the document clean again. The title bar and the status bar mark a dirty scene with a dot.
- **Save** (Ctrl+S) writes the file through a temporary file, so a crash never leaves half a file. Save As (Ctrl+Shift+S) writes a new file, which the editor then edits. Closing the editor or opening another scene with unsaved changes asks whether to save them.
- **No save during a drag.** While an undo entry is open, Save and Save As are disabled. This applies to a gizmo drag, a distance tool that waits, a drop and a scrub. A save that comes some other way is refused with a console line that names the owner. The reason: the entry's preview can still be put back, and the file must not keep a change that the scene no longer has while the document says that it is clean. Finish the edit or cancel it first, for example with Enter or Esc for a distance tool. If the close prompt's Save is refused, the scene stays open. A graph editor refuses Save during a node drag or a scrub in the same way.
- **Selection:** the selection is a list of entities. The last one selected is the primary one: the gizmo sits on it, and the properties panel names it. Ctrl toggles an entity in the outliner and the viewport, Shift adds, and Ctrl+A selects every entity. Delete and Duplicate act on every selected entity, without those under another selected entity, in one undo entry.
- **Selection by scene ID:** the editor keeps the selected entities' scene IDs, so a resync, which gives every entity a new handle, keeps the selection. An entity that an edit creates is selected when the host reports it. Entities that the game spawned have no scene ID, and the editor does not edit them.
- **Resync:** when the link connects, the editor sends the whole document as a scene snapshot (`Load_Scene`), with the scene's GUID, and the host replaces its world with it. With several scenes open, the snapshot has each of them (see [Several scenes](#several-scenes)). The world keeps the GUID, so the game loads what the scene's cooked blob lists, such as its navmeshes ([AI: Navigation](../ai/navigation.md#loading)). This is the same path after a crash, a host restart and a soft restart. The host reports a soft restart with an event, and the editor sends the snapshot again. The game loads its own scene at `init`, so without an open document the host shows that.
- **Opening a scene:** `--scene <file>`, or Open Scene (Ctrl+O), which opens it in place of every open scene. A file with an error does not open: its problems go to the console with their lines, and the open scenes stay. The title bar and the status bar show the active scene's file. Add Scene opens another beside it (see [Several scenes](#several-scenes)).
- **Rejected operations:** the host can refuse an operation, for example a field that the new DLL no longer has. It sends `Edit_Problems` with the entity's scene ID and the reason. The document keeps the operation, and the editor shows a warning on the entity, in the outliner and the properties panel, and in the console. A scene load sends its problems too, which replace the ones before them. The document is never changed to match the host.
- **The game's side** maps scene IDs to entities, in the game's table of scenes, `scene.Scenes`, which `editor.init` gets (see [World: Scenes](../world/scenes.md#scene-ids)). The maps are in the Level arena (see [Core](../core/jobs-and-memory.md#level-memory)): a load unloads the level and fills them again. A stale entry, such as for the game's own scene at `init`, makes the game build it again from every entity's `Scene_Entity`. The operations use the loader's procedures for an entity, a component or a field, so they convert values and report problems as a load does.

### Modes

| Mode | The game runs | Edits |
|---|---|---|
| Edit | Transform propagation, render extraction and editor rendering: the selection outline, the gizmo, the icons, the helpers and the debug lines. The edit phase, for the behaviours that run in edit mode, once the editor's scene is the world. No `Fixed`, `Update` or `Late` systems, and no other scripts. | Operations on the document, and the edit-mode behaviours' edits |
| Play | The full frame, as the game shows it: no editor rendering and no debug layer. | None. The outliner and properties show the host's world, read-only, with a tint. |
| Paused | As in Play, and the full frame of one fixed tick for each step. | None |

- **The game decides what runs.** The editor sends `Set_Mode`, and the game's editor package keeps the mode, because only the game knows what its frame runs. `editor.simulation` tells the game's frame what to run (`Simulation`) and with what time step: `Run`, the world with the frame's time in Play and one fixed tick for each `Step_Frame` while paused; `Edit`, the edit phase, in Edit once a `Load_Scene` of this session made the world the editor's document; `Wait`, nothing, while the editor has not answered the behaviours' last edits (see [Behaviours' edits](#behaviours-edits)); and `Hold`, nothing, otherwise. `editor.script_callbacks` gives the script runtime's level for it. A frame that does not run its world still propagates transforms (`ecs.update_transforms`), so edits of a parent move its children, and it still renders.
- **No script code outside Play, but the edit-mode behaviours'.** While the world does not run, the script runtime is quiet (`script.set_callbacks` with `.None`), or in Edit gives callbacks only to the classes with `edit_mode` (`.Edit_Mode`, see [Scripting: Edit mode](../scripting/behaviours.md#edit-mode)). In `Hold`, the game settles the world's changes into it each frame (`script.settle`), and in `Edit` the edit phase drains them. What follows holds for every other behaviour. A behaviour whose entity a scene load or an edit removes ends without `on_disable` or `on_destroy`, and its memory is free. One that an edit deactivates stops its coroutines, and gets `on_disable` when quiet ends: at Play, or at a paused step. One that an edit activates gets `awake` and `on_enable` in the first script phase of Play, and one that was awake before gets `on_enable` when quiet ends. One that an edit deactivates and activates again gets neither (see [Scripting](../scripting/behaviours.md#enabled-state)). Stop counts as Edit, so the behaviours of the play world end the same way when the scene replaces it: a `Load_Scene` settles the old world's behaviours without callbacks before the edit-mode ones run again. Paused is quiet too, except during the frame of a step. Without an editor, the world always runs. A game that an editor has just linked to is in Edit, and so is the fresh state of a soft restart.
- **The views show the game's frame alone outside Edit.** The selection outline, the gizmo, the light, volume and camera icons and their helper shapes, and the game's own debug lines are the debug layer, which `editor.draw_frame` gives the scene views only while editing, and the Game view never (see [Rendering](../rendering/layers-and-output.md#debug)). A click in a scene view still picks and selects, so the outliner and the properties follow it, and Stop brings the outline back on the selection that the editor sends again.
- **Play** (F5) starts the world that the game has, or goes on after a pause. It brings the Game document to the front, and opens it beside the Scene if it is closed, and the Game view takes the keyboard focus, so the game has the input at once (`EditorShell.Play`, `EditorViewport.RequestFocus`). Pause, Step and Stop leave the documents as they are. Behaviours that the scene loaded wake in the first script phase, so they get `awake` and `start` as for a scene load. The game's main script keeps running across a stop, as it does across a scene load.
- **Pause** (F6) stops the world where it is, and **Step** (F10) runs one frame of one fixed tick.
- **Each Play from Edit starts the world's `Random` sequence again** from its seed (`script.restart_random`), so the same play draws the same numbers. Play after Pause continues the sequence (see [Scripting: Random](../scripting/api.md#random)).
- **Stop** (Shift+F5) sets Edit, and the editor sends its scene again, which replaces the game's world. Nothing from play mode reaches the document. Restart Host has no shortcut now: its Shift+F5 went to Stop.
- **No edits while playing.** The shell refuses edits, undo and redo outside Edit, with a line in the console, and it has no document entity for the selection, so the properties panel shows the game's values read-only, there is no gizmo, and the outliner does not reparent. An edit that a drag has under way ends when play starts. Selection, visibility and lock still work. The Game view's frame and the status bar are green while playing and amber while paused.
- **Camera:** in every mode, the Game view shows the game's own camera and a scene view the editor's, so the user can fly around the world while it plays (see [Viewport](viewport.md#views)).
- **Input:** while the game plays and the Game view has focus, the Game view sends its input to the host as `Editor_Input` events: keys and buttons down and up, the mouse's position in frame pixels, the wheel, what each gamepad reports, typed text, and what an IME composes ([Input](../core/input.md#gamepads)). The host queues them in `core`, which applies them to the frame's `core.Input` after the window's own messages, so the game reads them as it reads a window. The function keys stay the editor's as well, so F5 and Shift+F5 work while the game has the keys. The other shortcuts do nothing while the game has them. Losing focus, and the editor's link closing, release every key and gamepad button, and the link closing also disconnects the gamepads.
- Entities that the game spawns at run time have no scene ID. The outliner shows them in play mode under their handle.

The mesh files that the scene's entities place are documents of their own beside the scene, `MeshDocument`s in a `MeshSet`, whose edits are `MeshOperation`s on the scene's undo stack, so one Ctrl+Z undoes the last thing the user did whichever file it touched; the host draws them from memory while they are edited (see [Mesh editing](mesh-editing.md#undo-and-saving)). Save writes the scene, then every dirty mesh.

### Behaviours' edits

A behaviour class with `edit_mode` runs in Edit too ([Scripting: Edit mode](../scripting/behaviours.md#edit-mode)). What it writes to the scene's entities is an edit of the document, as a game command's operations are, so it is saved and undone like any edit.

- **The game records, and does not apply.** The script runtime records the behaviours' writes to entities with a scene ID ([Scripting: Writes in Edit mode](../scripting/behaviours.md#writes-in-edit-mode)). The game's editor package turns them into operations by scene ID (`lib/engine/editor/behaviours.odin`) and sends them in `Behaviour_Operations`, with a ticket of their own, the ticket of the `Load_Scene` that the world has, and the class's name.
- **The editor applies them** to its document (`EditorShell.OnBehaviourOperations`), as its own commands make them: a destroy takes the descendants, a new parent keeps the pose in the world, and `Create_Instance` makes an instance of a prefab, as a drop does. While a drag has an entry open, the operations go into it, and a cancel puts them back with the drag's. Otherwise they make an entry under the class's name that follows the entry before it, so Ctrl+Z undoes both, and the world is again one that the behaviour has already answered. The document is dirty, as after any edit.
- **The answer:** applying the operations sends them back in `Apply_Operations`, and the editor then sends `Behaviour_Operations_Answer` with the ticket, on the same stream, so the game has the edit when the answer arrives. The editor refuses a batch, and answers false, without a scene, outside Edit, for a scene that it has replaced, or when an operation does not fit its document, which it then puts back and reports in the console.
- **The game waits for the answer.** While a batch is unanswered, the game runs no edit phase, so a behaviour never sees a world that lacks its own writes, and never writes them twice. After a refusal, it waits a second, or for the next edit, before it runs the phase again.
- **A behaviour must settle.** One that writes in every frame makes an entry for every answer, and one that writes after an undo makes a new entry, which drops the entries that redo would apply. A behaviour that writes only when the scene differs from what it wants, such as one that lays out its entity's children, stops after its first answer.

## Several scenes

A large world is several scenes, and the editor edits several of them at once, so a level designer works across the seams between them. Each open scene is a document of its own, with its own undo stack and dirty state, and the host's world holds them all.

- **Add Scene** (Ctrl+Shift+O, `EditorShell.AddScene`) opens a scene file beside the open ones, and makes it the active scene. A scene that is open already becomes the active one, and so does a scene that the content browser opens. **Open Scene** opens a file in place of every open scene, and asks about the changes of all of them first. **Close Scene** (`CloseScene`) closes the active scene, after it asks about that scene's changes; the last open scene does not close. A prefab opens alone, as the document (see [Prefabs](prefabs.md#editing-a-prefab)): Add Scene refuses one, and refuses to add a scene beside one.
- **The active scene** is the one that edits, Undo, Redo, Save, Save As and the undo history act on (`EditorShell.Scene`; `Scenes` has every open one, in the order they were opened). Selecting an entity of another scene, in the outliner or the viewport, makes its scene the active one, and so does a click on the scene's heading in the outliner. A change of the active scene ends the open undo entry for its owner, as Play does (see [Document model](#document-model)), and clears a selection whose primary entity is another scene's. The selection's other entities stay selected, but Delete, Duplicate and the properties panel take only the active scene's.
- **Each scene keeps its own history.** Ctrl+Z undoes the active scene's last entry and leaves the others as they are. Save writes the active scene's file alone, so the other scenes stay dirty and their files unchanged. **Save All Scenes** writes every dirty one. Closing the editor, or Open Scene, asks about every dirty scene at once, and its Save saves them all. Each scene has its own autosave, and an autosave that is newer than a scene's file is offered when that scene opens. The mesh documents and the landscape maps are the editor's, not a scene's: a save of any scene writes the dirty ones, and they stay open until Open Scene replaces every scene.
- **Scene numbers.** The editor gives each scene a number when it opens it (`SceneDocument.Number`), from 1, and never uses a number again in a session, so an edit that names a closed scene never edits another. Scene IDs are unique only in their scene: two scenes, such as a copy of a file, can have the same. So the host's world keys an entity by its scene's number and its scene ID. `scene.Scene_Entity` has both (`id` and `scene`), `Entity_Info` and `Pick_Hit` carry both, and the editor's world mirror finds an entity by both (`WorldModel.FindScene(scene, id)`). The game's own scene, which it loads without an editor, is 0.
- **`Load_Scene` has every open scene**, each with its number, its GUID and its entities (`Loaded_Scene`), and the host replaces its world with all of them: it unloads the level, and adds each with `scene.add_scene` under its number. The editor sends it again when a scene opens or closes. A scene's references and parents resolve in that scene alone: an entity cannot refer to, or be a child of, another scene's. The world keeps the first scene's GUID, so the navmeshes of the first scene load (see [AI: Navigation](../ai/navigation.md#loading)).
- **Operations name their scene.** `Operation.scene` is the number of the scene whose entity it edits. The editor sets it as it sends a document's operations (`EditorShell.SendOperations`), and the game finds the entity with `scene.find(scenes, w, scene, id)`, which keeps a map of scene IDs for each scene. `Edit_Problems` names the scene of each problem, and the editor keeps the problems by scene and scene ID.
- **The game's edits.** An edit-mode behaviour's edits and a game command's operations name the scene of the entity that they edit (`editor.scene_number` for a command). One with a scene of 0, as a behaviour's new entity at the root has, edits the active scene. A batch that edits two scenes makes an entry in each, each following the entry before it in its scene. A batch that names a scene that is not open is refused.
- **The outliner** shows every open scene's entities. With more than one scene open, each scene's entities are under a heading with the scene's file, a dot while it is dirty, and the active scene in bold. A click on a heading makes its scene active, its arrow collapses it, and its menu makes it active, saves it or closes it. A row of a scene that is not active hides, locks and shows its problems as the active scene's rows do. A row drags onto another row of its scene only. A prefab or a script dropped on another scene's row makes that scene active first (see [Shell: Outliner](shell-and-panels.md#outliner)).
- **Hidden and locked entities** are each scene's: the editor keeps them by scene and scene ID, and writes each scene's under its own file in `scene-views.json`.
- **The title bar** names the active scene and how many others are open, with a dot when any of them is dirty.
- **What is the active scene's:** the gizmo, the properties panel, mesh mode, the landscape tools, a material dropped in the viewport, and a new entity of the Add menu act on the active scene's entities. A double click in the viewport on another scene's entity selects it, which makes its scene active, before mesh mode enters on it.
- **Streamed scenes:** the game loads and unloads scenes one at a time while it runs, with numbers from `scene.FIRST_RUNTIME_SCENE` that no editor scene has (see [World: Scenes](../world/scenes.md#numbers)). The editor does not edit them.
- **Not yet:** the editor sends every open scene again when one opens or closes, as one `Load_Scene`, rather than adding or removing the one scene. A prefab does not edit in a tab of its own beside the scene: it still opens alone.

## Scenes

A scene is a source asset with a GUID and a `.meta` file, like every other asset (see [Content pipeline](../content/identity-and-cooking.md#identity)). The cooker parses scenes with `asset_format.scene_parse`, and the editor with `SceneFile` in `Cinnabar.Editor.Document`. The two must agree.

- **Scene IDs:** each entity in a scene has a 64-bit random ID, nonzero and unique in its scene. Operations, the link and the scene file use scene IDs. The host maps them to entity handles, which change on every load. The loader gives each entity a `Scene_Entity` component with its scene ID, and `Entity_Info` carries it to the editor.
- **Text source:** a scene file is text, so it diffs and merges. It starts with `scene 2`, the format's version, and both readers take `scene 1` too, which has no prefab instances. It has one block per entity, sorted by scene ID, so an edit changes only the lines of the entity it touches. Fields are written by name. A line that starts with `#` is a comment, and the editor keeps only the comments before `scene 2`.
- **Entity keys:** an entity block has `name`, `parent` (a scene ID) and `active = false` for a disabled entity, then its `component` and `behaviour` blocks with their fields indented. An instance of a prefab adds `prefab`, and its override blocks `removed` and `remove` lines ([Prefabs](prefabs.md#instances-in-a-scene)). An entity key that the editor does not know is a warning, and the editor writes it back unchanged.
- **Values:** `true` and `false`; a number, or an array of up to four numbers such as `[0, 0.7071068, 0, 0.7071068]`; a quoted string with `\"`, `\\`, `\n` and `\t`; a scene ID after `@`, such as `@1b04c7e95a2f3d88`, or `@0` for none; an asset's GUID after `$`, such as `$9db8150cc7215ffc2708d20d77cf60bf`, or `$0` for none; and a bare word, such as an enum value's name. A number written as an integer is kept exactly. The writer gives every float a point or an exponent, so it reads back as a float.
- **Components by stable ID:** a component block gives the [stable ID](../world/ecs.md#ecs) and the type's name. The loader uses the ID. The name is for people and for error messages.
- **Positions** are raw `i64` values (see [World](../world/positions-and-transforms.md#where-positions-go)), so a scene round-trips exactly. The editor shows meters.
- **Unknown data round-trips.** A component ID or a field that the current DLL does not know is kept, written back unchanged, and reported as a warning. A broken build therefore never deletes scene data.
- **Behaviours** are written by script GUID, with their field values by name.
- **Names:** the engine's `Name` component holds up to 63 bytes in the component itself, because component storage holds no pointers. A longer name is cut at a character boundary. The outliner and the properties panel show names, and `Entity_Info` carries them.
- **Prefab paths:** an entity in a prefab instance is identified by a path: the instance's scene ID, then `#` and the entity's scene ID in the prefab, such as `5f3a9c01e2b47d10#a90b3e7f15c4d2e8`. A prefab in a prefab adds a level for each nesting. The prefab's asset GUID is not in the path, because every instance of a prefab has the same one. The path stays the same when the prefab changes, so overrides in the scene still find their entities. A reference to such an entity is `@` and the path, and its scene ID once the instance is expanded is the path's hash, `scene_path_id` ([Prefabs](prefabs.md#expansion)).

A sketch of the format:

```
scene 2

entity 5f3a9c01e2b47d10
name = "Door"
parent = @1b04c7e95a2f3d88
component 1 Transform
	position = [16777216, 0, -754974720]
	rotation = [0, 0.7071068, 0, 0.7071068]
	scale = [1, 1, 1]
behaviour 9d2e41c0b7a35f6e81c4d2a90b3e7f15
	open_angle = 90
	trigger = @7a11e0c3d94b2f56
```

**Cooking:** the cooker cannot lay out native components, because their types exist only in the DLL. The cooked blob therefore stores each field as a tagged value with the hash of its name (see [Content pipeline](../content/kinds/scenes.md#scenes)), and the scene loader in `lib/engine/scene` matches them to the fields of the registered types at load. The same code applies a snapshot from the editor.

**Loading** replaces every entity in the world, between frames, with `ecs.despawn_all`. After it, the world gives out the freed slots from the lowest index up, so the handles, and with them the outliner's order, follow the scene's order. The loader spawns every entity before it sets any field, so a field can refer to an entity later in the file.

- A field that the scene does not set is zero. A value is converted to its field's kind: an integer must fit, an enum takes a name or an integer, a position takes three integers, and an entity takes a scene ID.
- What the world cannot use is skipped with a warning, and the rest of the entity still loads: a component that the game does not register, a field that its type does not have, a value that does not fit, a scene ID that is not in the scene, or a behaviour field that the class does not declare.
- `Previous_Transform` starts equal to `Transform`, so nothing interpolates from where the old world was. Behaviours wake in the next script phase.
- The `Name`, `Parent`, `Inactive` and `Scene_Entity` components come from the entity's keys, so a component block for one of them is ignored.
- A component that cooked scenes use gets an explicit ID (see [World](../world/ecs.md#component-registry)). The sample game's components are 1001 and up.
