# Editor link

The message connection between the editor and the host, its framing, schema and generated C#, and the game side that mirrors the world to the editor.

**In this document:** [Editor link](#editor-link) · [World](#world)

## Editor link

The editor link is a message connection between the editor and the host. It uses TCP over loopback.

- **The host is the server.** It listens on `127.0.0.1` at the port that `--link` gives, so only the local machine can connect. It serves one editor at a time and refuses a second connection. The editor picks a free port, starts the host with it, and connects, retrying while the host starts. It connects again after a host restart.
- **Framing:** each message is a 12-byte little-endian header (payload length, kind, flags, request ID) and a payload of at most 64 MiB. A response has the request ID of its request. An event has request ID 0.
- **Wire format:** numbers are little-endian as they are in memory, a `bool` is one byte, enums are their backing integer, and strings and slices are a `u32` count followed by their bytes or elements. A fixed array has no count, and a struct is its fields in order. A payload that does not decode to exactly one message is refused.
- **Handshake:** the editor sends `Hello` with its protocol version. The host answers `Welcome` with the game's name and the DLL's layout hash, or `Refused` with both versions. The editor then stops the host and shows the reason (see [Crash recovery](processes-and-projects.md#crash-recovery)).
- **Two handlers.** The host handles the messages that need no game state: the handshake, the Game view's size, the viewports' frame acknowledgements, the capture source and input, and it sends its own stats. The game handles the mode, because only it knows what its frame runs. It passes every other message, still encoded, to `Game_API.editor_poll`, once per frame between frames, with the connection (0 while no editor is linked). The game decodes them with its own copy of `lib/engine/editor/link`, and appends its own messages to a buffer that the host owns, which the host then queues. The game cannot write to the outbox directly: it logs while it polls, and the logger takes the outbox's lock. Type info for game-side types exists only in the DLL's image, so the editor never reflects over game types itself.
- **Threads:** in the host, an accept thread waits for the editor, a reader thread queues its messages, and a writer thread sends the outbox. The main thread handles the queued messages between frames, after the reload point, while no job runs. Events of a frame go out at the end of it. The server is `lib/engine/wire/serve`, which the cook daemon also uses, and stopping it joins every thread that it started.
- **The linked editor:** the server owns the connection and whether it is linked, under one lock. The main thread answers a `Hello` with `Welcome`, and then links that connection. The link fails if that connection closed in the meantime. The host's events, such as `Host_Stats`, go only to the linked editor. Only the answer to its `Hello` goes to a connection that is not linked.
- **The log:** while an editor is linked, the host's logger sends every line, the game's and the jobs' included, over the link instead of to the host's console. The logger asks the server under its lock. A line never goes to an editor before its `Welcome`, and once the editor leaves, the next line goes to the console. A line carries its level, time, location and text. If more than 16 MiB is waiting to be sent, log lines are dropped and counted. The editor's console also shows the host's own console output, which has the lines before the link and anything that does not go through the logger, such as a crash.
- **One schema:** the messages are Odin structs in `lib/engine/editor/link`, a package that imports nothing from core or engine, so the host and the game both use it. The framing, the wire format and the schema writer are in `lib/engine/wire`, which the cook link shares (see [Content pipeline](../content/daemon-and-operations.md#cook-link)). `just link-schema` runs `host --emit-link-schema`, which writes `build/obj/link/link-schema.json`, and `cook --emit-link-schema`, which writes `build/obj/link/cook-schema.json`, and a C# source generator for `Cinnabar.Editor.Link` reads both. A message's kind is its index in the `Message` union, and the protocol version is a hash of the schema, so any change to a message changes the version. A changed message is a build error in the editor, not a decode error at run time. Odin's `Snake_Case` names become `PascalCase` in C#.

To add a message: add a struct to the `Message` union in `lib/engine/editor/link`, handle it in the host or in `editor.poll`, run `just link-schema`, and the editor's build gives the C# record. The compiler then finds every place that must handle it.

### Profile

The host's profiler ([Core](../core/profiling.md#profiler)) talks to the editor's [profiler panel](shell-and-panels.md#profiler) without the game: every zone is the host's, so the host handles every profile message.

- **`Profile_Summary`** goes out right before each `Host_Stats`, for the same interval: the CPU, wait and GPU times' averages and most, the frames with the longest CPU and GPU times, the zones that the threads dropped, whether the host records, and the costs per frame of each pass, system and script callback, with their names as text.
- **`Profile_Capture_Request`** asks for a frame: the next one, the longest of the last `count`, or one by number. The editor gives it an `id`, and the host answers with a **`Profile_Capture`** with the same `id` once the frame has ended and its GPU times are in, or have not come for 8 frames. A frame that the host no longer has comes back with `available` false and a `reason`.
- **A capture** has a table of the names that it uses, its lanes (each thread, then the graphics and the compute queue), and its zones. A zone's start is in nanoseconds from the frame's start, its name an index into the table, and its lane an index into the lanes. GPU spans are zones on the GPU lanes. 10,000 zones are about 150 KB.
- **`Profile_Recording`** starts or stops the recording of zones. The host records again when the editor disconnects.

## World

The game's side of the link is `lib/engine/editor`. The game keeps an `editor.Editor` in its `Game_State`, and its `Game_API.editor_poll` calls `editor.poll` with the world and the script runtime. On the editor's side, `WorldModel` in `Cinnabar.Editor.Model` mirrors what it hears. The mirror is read-only: it changes only through the game's messages.

- **A new connection gets everything.** When `poll` sees a connection that its session is not for, it ends the session and starts another, and it sends `Component_Types` and an `Entity_Snapshot` (see [A new game state](#a-new-game-state)). After a `Load_Scene`, it sends an `Entity_Snapshot` again, and forgets the watches, the selection and the hidden entities, whose entities are gone. After an `Add_Scene` or a `Remove_Scene`, it scans at once and sends an `Entity_Delta`, as the other scenes' entities keep their handles, and it forgets only the removed scene's entities in the selection and the hidden entities. A soft restart makes a fresh `Game_State`, which knows no connection, so the editor gets everything again then too. A snapshot replaces the editor's mirror, and the editor sends its watches, its selection, its hidden entities and its mesh overlay again after one, because they name entities by handle.
- **Deltas:** at most ten times a second, the game scans the world with `ecs.world_iter_changed` and compares each entity slot with what it last told the editor: the handle, the archetype (which stands for the set of components), the parent, the active state and the name. It sends an `Entity_Delta` with the changed entities and the destroyed ones. The scan visits only the chunks where a row arrived, or where `Parent` or `Name` was written, since the last scan (see [ECS: Change versions](../world/ecs.md#change-versions)): a change of archetype or of active state moves the row. If any entity was despawned since the last scan, a sweep over what the game told the editor finds the ones that are not alive. A slot that a new generation took therefore counts as a destroyed entity and a new one. The profiler shows the scan's cost in its own zone, `Editor delta`, or `Editor snapshot` for a full scan, inside `Editor poll` (see [Profiling](../core/profiling.md)).
- **Watching:** the outliner needs every entity, but only a few entities need their field values. The editor sends `Watch_Entity` and `Unwatch_Entity` for the selection, and the game sends `Entity_Values` for each watched entity at most twenty times a second, and only when the encoded values changed. A watched entity that dies stops being watched. At most 64 entities are watched.
- **Values are bytes.** A component's value is its memory, and the editor reads each field at its offset with `FieldValues`, so the game does no per-field work. A behaviour's fields come from `script.inspect`, which reads the instance's table for each field that `Behaviour.define` declared, without calling any script code. A behaviour's value also names the script asset whose module returned its class, which is how the document finds it.
- **Values are the document's.** An override can hold a field of a watched entity (see [Overrides](#overrides)). `Entity_Values` then has the document's value of the field, not the world's, and `held` names the field. The properties panel shows the document's value, and it marks the field's name.
- **And what the world shows.** For an entity with a held field, `Entity_Values.shown` has each of its components as the world shows them, with the overrides and the cutscene preview laid, and `shown_preview` has the preview's ticket and time then, or a ticket of 0 without a preview, the file time of the unsaved blob that it played, or 0 for the saved one, and the serial of the `Cutscene_Preview_Values` that showed over it, or 0 for none. The game takes them before a poll lifts the overrides, so they come one poll after a hold or a watch begins. The cutscene editor keys them (see [Cutscene editor: Keying](cutscene-editor.md#keying)).
- After a code reload, the game sends the types again, and the panels rebuild.

### Overrides

An override is a set of values that an owner in the editor writes over the game's world in Edit. It is not a part of the document. It sends no operation, makes no undo entry and does not make the scene dirty. Save works while an override is on, and the file holds the document's values. Previews such as an animation's pose or a light's flicker can use overrides. The cutscene editor's preview does not: the game evaluates the cutscene itself, and lays its writes with the overrides (see [Cutscene editor: Preview](cutscene-editor.md#preview)).

- **Tokens.** An owner calls `EditorShell.Overrides.Begin` and gets an `OverrideToken`. The editor gives each override a number, and the number only goes up, so the game drops a late message for an override that ended. `Begin` gives no token while the host is not linked or the editor is not in Edit. A token that ended does nothing, and its `Ended` event tells the owner once why it ended (`OverrideEnd`). `WorldOverrides.End` is the one place where a token ends.
- **One message for each frame.** `OverrideToken.Write` sends one `Override_Frame` with all the override's writes for the frame. The frame is the override's whole state. What an earlier frame wrote and this frame does not goes back to the document's value. A frame writes:
  - a component's field, by the component's ID and the hash of the field's name (`format.scene_field_hash`), as a scene names it;
  - an entity's pose, in its own space, without interpolation: a root's `Transform` through `ecs.teleport`, or a child's `Local_Transform`;
  - an Animator's driven samples (see [Animation: Driving an Animator](../animation/design.md#driving-an-animator));
  - a camera on the stack of a game view (see [Cameras](../world/cameras.md#stacks));
  - instances of prefabs that live while the override has their keys in its frames.
  
  An entity is a document entity, by its scene's number and its scene ID, as operations name it, or a spawned entity, by its key. The game turns each field's value into bytes once, when the frame comes. It logs a write that it cannot apply, and applies the frame's other writes.
- **Lift and lay.** The game keeps each override's last frame in the `Session` (`editor/overrides.odin`). `lay_overrides` writes the frames over the world, in the order that the overrides began, and saves each value before it writes over it. `lift_overrides` writes the saved values back, the last first. The game lifts the overrides while anything reads or edits the document in the world: for all of `poll`, for the edit phase, and for the script reloads at the end of each frame. `send_behaviour_edits` sends no edits that behaviours made while the overrides were on the world. So the editor's operations, the edit-mode behaviours' edits and what the game sends the editor all see the document. An edit of a field that an override holds goes to the document's value, and the override stays on top. When the override ends, the newest document value shows. Camera pushes, drives and spawned entities are not lifted. They stay from frame to frame, so a view does not cut again and a drive does not start again.
- **Two overrides of one field.** The later one shows. When one of them ends, the other one's value shows, or the document's when none is left.
- **The end.** `Release_Override` ends an override. The world goes back to the document's values, the cameras pop, the drives end and the spawned entities despawn, all in the same poll. The game also ends every override, and tells each owner with `Override_Ended`, at these times:
  - a `Set_Mode` (`Mode`): Play and Pause run the document's world, and Edit waits for the editor's scene;
  - a `Load_Scene` (`Scene_Loaded`);
  - a code reload, after the new DLL has registered its components (`Code_Reloaded`).
  
  A `Begin_Override` outside Edit, or before the editor's scene is the world, gets `Not_Editing`. A `Begin_Override` when 16 overrides are on gets `Full`. When the editor's link closes, the game ends the overrides and the world shows the document, and the editor ends its tokens with `LinkClosed`. `Add_Scene` and `Remove_Scene` do not end overrides: a write to an entity that is gone is skipped.
- **Marks.** `Overridden_Entities` names the entities that overrides write or spawned, when that set changes. The outliner marks them with ◆. `Entity_Values.held` names the held fields of a watched entity, and the properties panel shows their names in italics. Gizmos read the document, so they show the document's pose, except for an entity whose drag goes to the cutscene that holds the preview, which they show where the world shows it (see [Cutscene editor: Gizmo keys](cutscene-editor.md#gizmo-keys)).

### A new game state

A new link, from a start, a restart or a crash, and a soft restart both give the editor a game state that knows nothing that the editor sent. A code reload keeps the game state, so it is not one.

- **The game's side.** What one connection has sent the game, and what the game has sent it, is the `Session` in `editor.Editor`: the entities that the editor knows and watches, the selection, the hidden entities, the picks, the Navigation Path tool's points, and each viewport's kind, camera, gizmo, settings and target (`View`), the mode, the previews and the thumbnail, the live meshes and the mesh overlay, the overrides (see [Overrides](#overrides)), the cutscene preview (see [Cutscene editor: Preview](cutscene-editor.md#preview)), and when the game last sent each kind of update. `begin_session` starts one and `end_session` frees it, closes its previews and its viewports, and zeroes it, at `init`, at `destroy` and for each new connection. State that a new editor must not inherit goes in `Session`, so `end_session` frees it. The viewport tools' GPU objects, the commands, the UI state and `by_scene_id` stay outside it. A pick that the GPU still runs comes back with an old ticket, which the next session ignores.
- **The editor's side.** `EditorShell.OnNewGameState` is the one handler. A new link and a `Game_Reloaded` of kind `Soft_Restart` both call it. It clears every cache of what the game was sent, drops every request that waits for the game, and sends again:

  | What | Message |
  |---|---|
  | The mode, which the editor resets to Edit, as the game does | none |
  | The open scene | `Load_Scene` |
  | Each shown viewport | `Open_Viewport` |
  | Each shown scene view's camera, gizmo and box handles | `Editor_Camera`, `Gizmo_State`, `Box_Handles` |
  | The selection and the hidden entities | `Set_Selection`, `Set_Hidden` |
  | Each shown viewport's settings | `Set_Viewport_Settings` |
  | The Game view's size, if it has had one | `Game_Size` |
  | The viewport that captures read | `Capture_Source` |
  | The mesh overlay | `Mesh_Overlay` |
  | The Navigation Path tool's points | `Nav_Probe` |
  | The live meshes | `Live_Mesh` |
  | Each open preview, with what it shows | `Open_Preview`, `Preview_Settings` |
  | The cutscene preview's tab, at its playhead, with a new ticket, after the scene | `Cutscene_Preview_Open` and `Cutscene_Preview_Settings`, then `Cutscene_Preview_Play` at its rate if it played |

  It ends every override token with `NewGameState`, and sends no override again: the new state has none, and each owner begins again if it needs to. It drops the picks and the `Sky_Sun_Request` in flight, disconnects the previews from the old targets until the new `Preview_Target`s come, and restarts the thumbnail queue, whose bake the old state lost. A preview's `unsaved` flag follows the cook daemon's cache, not the game, so `Open_Preview` sends it again as it is. A new feature that keeps a copy of game state, or waits for an answer from the game, resets it in `OnNewGameState`, and nowhere else.

### Types

- A component type gives its stable ID, its name, its category, its size and its fields. The category is the folder in which the Add Component picker offers the type, or `-` for a type that the picker leaves out (see [Shell: Properties](shell-and-panels.md#properties)). A field gives its name, offset, kind, read-only flag, range and color flag, and an enum's backing kind and named values.
- **Field kinds:** the integer and float types, `bool`, enums, `[2]f32`, `[3]f32`, `quaternion128`, `World_Position` and `Entity`. A nested struct that is none of these adds its fields with dotted names, such as `inner.amount`. Other fields are hidden. *Asset references come with asset fields.*
- **Struct tags:** the `editor` tag is a list of words with spaces between them. `-` hides a field, `read` makes it, and anything in it, read-only, `range=0,100` gives a slider range, and `color` marks a `[3]f32` as a linear color, as in `editor:"color range=0,1"`. The walk follows the same rules as `script.expose`. The `Behaviours` component's Luau reference is hidden this way. The walk is `scene.component_fields`, so a scene can set exactly the fields that the editor shows.
