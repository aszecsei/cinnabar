# Animation graph editor

The animation graph editor edits an animation graph (see [Content: Animation graphs](../content/kinds/animation-graphs.md#animation-graphs)) and shows it playing (see [Animation](../animation/design.md#design)). Each open one is a document beside the viewport, `AnimationGraphEditorDocument`, over an `AnimationGraphEditor` in the shell, which holds its state, so docking can rebuild the view, and tests drive the editor without a window.

**In this document:** [The file](#the-file) · [The canvas](#the-canvas) · [Preview](#preview) · [Live view](#live-view)

## The file

`AnimationGraphFile` reads a graph's text as whole lines (`TextLine`, which the decision editor's files share), each in the block that `tools/cook/animation_graphs.odin` would read it in: the settings, each parameter, each clip with its events, each node with its fields, and the rest. Unlike a material's writer, it does not write the text again from a model.

- **Round trip:** a file reads and writes back as it was, with its comments, its blank lines and each line's ending. An edit changes only the value of a field, keeping its indent and its comment, or adds or removes the lines of a block. Opening a file does not make it dirty, and a node without a `position` gets a place on the canvas that is not written.
- **It reads only the structure.** What a block's lines mean, and whether they are right, is the cooker's to say, so a graph with problems still opens, with its problems on its nodes. Only a file whose first line that is not a comment is not `animation_graph 1` is refused, and that opens in the script editor, with the reason in the console.
- **It agrees with the cooker.** `tools/cook/testdata/animation_graphs` has files that the cooker's tests and the editor's both read, with a comment on each line that the cooker reports and a list of the nodes that it reads. The rules that they pin are where a block ends, what is not a node, and which line of a repeated field counts.
- **Undo:** each editor has its own undo stack of the graph's text before and after each edit (`GraphDocument`, which the material, UI and decision editors' documents share), and a drag is one entry. Undo, Redo and Save act on the graph editor whose document is active. Save is disabled during a drag, because its steps can still be put back (see [Document model](document-and-scenes.md#document-model)). A document is dirty when its position in its history is not the one that its file has, and its tab marks it with a dot.
- **Saving** writes the text through a temporary file, and the cook daemon then cooks it. Nothing reads the file again while it is open, so a save that would replace what another program wrote asks first. The toolbar opens the text in the script editor, which is how a clip's events are edited for now.
- **Closing** an editor with unsaved changes asks to save them, and so does closing the editor. An open graph follows its file when the content browser moves or renames it.

## The canvas

- **Layout:** the [preview](#preview) over the graph's entry state and root motion joint, its parameters and its clips on the left; the canvas; and the selected node's fields on the right. The panel's rows have the problems on their lines.
- **The canvas** (`AnimationGraphCanvas`) draws the two kinds of connection differently, because they are different: a transition joins whole states, and a blend feeds what one state plays. It has no ports. A state is a place in the machine, a rounded body in a thick rim, which its transitions' arrows start and end on, with a chip that names what it plays. A blend is not a place in the machine, so it has square corners and no rim, and nothing arrives at it. A strip along its foot says which states play it, and a dotted tether with no head joins it to each of them, whose chips turn the tether's color. A transition is an arrow through a glyph, at its `position` or else on the arrow, which shows its `when` or its exit time. Arrows between the same two states keep to lanes, so one and the one back do not lie on each other. From any state, only the arrow to its state is drawn. A transition that names no state still has a glyph to select it by. The entry state's name has a mark. The geometry and the hit test are `AnimationGraphGeometry` in `Cinnabar.Editor.Tools`.
- **Mouse and keys:** the left button selects a node or a transition (Shift adds, Ctrl toggles), drags what is selected, and drags a box. These gestures, the pan, the zoom and the keys below are those of every graph canvas, `NodeGraphCanvas`, which the [decision editor](decision-editor.md#the-canvas) shares. A drag from anywhere on a state's rim to another state adds a transition, which leaves after one play; the rim lights and the cursor changes where a press would start one. A drag from the strip along a blend's foot to a state makes the state play it; a tether dragged off a state's chip moves to another state or is removed. The right or middle button pans, and a right click without a drag, Space or Tab adds a state or a blend. The wheel zooms about the mouse. Delete deletes what is selected, F frames the graph, and Escape cancels a drag.
- **Deleting** a state takes the transitions from it and to it with it, in one undo entry. A blend leaves the states that played it without a motion, which the cooker reports.
- **Details:** a state's name, motion, speed, loop and events; a blend's parameter and inputs, which stay numbered from 0 without a gap; and a transition's from, to, conditions, exit time and duration. Earlier and Later change which a state tries first among its transitions, since their order in the file is the graph's. From any state, a transition has no exit time.
- **Names:** a new name reaches what reads it. A state's goes to the transitions and the entry, a parameter's to the blends and the first word of each term of a condition, and a clip's to the states and the blends. A name that the cooker would refuse, or that another has, is refused, with a warning in the console.
- **Problems:** a moment after each change, and when it opens, the editor sends the graph's text to the cook daemon in `Cook_Preview`, which checks it and writes nothing (see [Daemon](../content/daemon-and-operations.md#cook-daemon)). The answer's problems go on their nodes by the lines of the text that it was given, as a dashed red frame and in the details, and the others on the panel. An answer about a text that has changed since is dropped, as another check follows. Closing the editor cancels a check that waits and drops the answer of one that runs, and the closed preview sends the game nothing more. The cooker does not look up a clip's GUID, so the editor does: a clip that names no animation in the index is a warning on its row.

## Preview

Each editor plays its graph on a mesh by itself, in one of the game's previews, at most four at once with the material and effect previews (see [Rendering: Material previews](../rendering/materials.md#material-previews)). It plays in every mode, apart from the world: no entity, script or physics takes part, so what you set stays set, and nothing in the scene or the game changes.

- **The mesh** is the first of the model that the graph's first clip comes from, until another is picked on the panel. It draws in the default material. Dragging turns the camera about it, and the wheel moves it nearer or farther. A mesh without a skin draws at rest.
- **The graph** is the one being edited: a moment after a change, the cook daemon cooks a text without problems into the cache's preview area, and the preview starts it again, keeping the parameters that it still has. A text with problems leaves the last good one playing.
- **Parameters** are on the panel, from what the preview plays. A float is a slider over what the graph compares it with and what its blends' inputs are at, a bool a check box, and a trigger a Pull button; a slider holds its value during a drag, as the values come back. A trigger lasts one tick whether a transition takes it or not: `look` does nothing to the fox unless it is in `move`. Restart goes back to the entry state, with the parameters at their defaults.
- **The canvas** shows what the preview plays, as it does the [live view](#live-view), unless the game is playing this graph on the selected entity.
- **The game's side:** `anim.preview_pose` moves an instance that the preview keeps by the time since it last drew, from the blob, and leaves out root motion so the mesh stays in view. A graph that cannot pose tries again a second later. `Restart_Preview`, or an `Open_Preview` of another asset, starts the graph over: a new instance, which poses at once. `render.Preview_Desc` takes the palette, and a compute pass poses a copy of the mesh that the preview keeps, with the same shader as an entity's. The link has `Animator_View` with an entity of 0, `Set_Preview_Parameter` and `Restart_Preview` (see [Editor link](link.md#messages)).

## Live view

While the game plays or is paused, the selected entity's Animator shows on the canvas when it plays this graph. Otherwise the panel says why not, or which graph it plays.

- **The link.** The game sends `Animator_View` for each watched entity once after the watch, then when it changes: the graph's GUID, the current state, the state that it fades from and the last transition by their node IDs, which the blob keeps, the fade, the state's progress, and each parameter's name, kind and value (see [Editor link](link.md#messages)). An Animator's component holds the same instance, but its bytes are not named, and its states are the blob's indices. When the Animator or its ready graph goes, one empty view says so. An entity without one sends an empty view after its watch, so a view that the editor kept from an earlier watch, which an unwatch does not drop, goes.
- **The canvas** lights the current state's rim, with a bar for its progress through this play, and the rim of the state that it fades from by what is left of the fade. The last transition's arrow and glyph are lit, brightly during its fade. An interrupted fade has no one state that it fades from, so only its transition shows. A node that the document does not have, as when it has changed since it last cooked, has no place to show.
- **It only looks.** The panel says what plays, and nothing there writes to the game: a parameter is set in the [preview](#preview), where nothing overwrites it, as a script in the game can.
- **Saving during play** makes a new blob, so the graph starts again in its entry state, keeping the parameters that it still has (see [Animation: The instance](../animation/design.md#the-instance)).
