# Presentation

The frame target, output modes for SDR and HDR displays, and shared mode, in which the host renders into shared textures that the editor reads.

- The game renders into a frame target texture that `core` provides. The engine never sees a swapchain.
- The frame target is in the render target layout when the frame starts, and the game must leave it in that layout. Its contents are undefined at the start of each frame.
- `core` reads the window size once at the start of each frame. The frame target has that size, and `window_size` returns it for the whole frame. While the window is minimized, the size is zero and the game renders nothing.
- **Standalone:** `core` copies the frame target to the swapchain and presents with vsync. Vsync paces the frame.
- **Output modes:** `gpu_output` gives the frame's `gpu.Output`: its `Output_Mode`, the frame target's format, which follows from the mode (`output_format`), and the `Display`. `Sdr` is `FRAME_TARGET_FORMAT`, with an sRGB view. `Hdr10` is `RGB10A2_Unorm`, with Rec. 2020 primaries encoded with the PQ curve of SMPTE ST 2084. `Scrgb` is `RGBA16_Float`, linear with Rec. 709 primaries, where 1 is 80 nits. `gpu_request_output` asks for a mode from the next frame on. Its default, `Auto`, is `Hdr10` while the display is in HDR. Set `CINNABAR_OUTPUT` to an `Output_Request` name, such as `CINNABAR_OUTPUT=Scrgb`, and `core` ignores the game's requests and uses that one. Shared mode is always `Sdr`, because the editor reads its textures as sRGB. See [Rendering](../rendering/layers-and-output.md#hdr-output).
- **The display** is the one that shows most of the window: whether the desktop is in HDR on it, its luminances from DXGI, and its SDR white, the brightness that Windows gives SDR content in HDR, from the display configuration. DXGI does not report the SDR white. The D3D12 backend finds the display again every 60 frames, and at once when its factory is no longer current, because the adapters or outputs changed, for example when HDR is turned on or off.
- **A change of mode** waits for the GPU, gives the swapchain's buffers the new format, and sets the swapchain's color space. A mode whose color space the swapchain cannot present falls back to `Sdr`, and is not tried again. The frame target keeps its handle, and its description has the new format, so a pipeline that draws into it needs a version for each format.
- **Editor:** `core` renders into shared textures and signals a shared fence instead (see [Editor](../editor/viewport.md#viewport)). `host --shared <name>` selects this: the window is hidden, and nothing presents. The frame target has the window's size until the editor asks for another one with `core.resize_shared_target`. Each size is a generation of the shared target, and its objects are named `<name>.g<generation>.texture0..2` and `<name>.g<generation>.fence`. The D3D12 backend renders frame k of a generation into texture k % 3 and then signals k on the generation's fence, so a reader that sees fence value v reads texture v % 3. Frames count from 1 in each generation. A resize waits for the GPU, releases the old objects and makes the new ones, and readers keep the old ones alive until they open the new ones. A frame ends with its texture in the common layout, which other processes can use. The textures have the frame target's typed format, because D3D11 cannot open a shared typeless texture, and the editor reads them with D3D11. A high-resolution 60 Hz timer paces the frame. `--adapter <luid>` makes the host use the GPU whose LUID it gives, in hex, because shared objects open only on the adapter that created them.
- **Back-pressure:** while the editor is linked, `core.pace_shared_frames` is on, and the backend renders frame k into a shared texture only if k is at most the reader's acknowledged frame + 2 (`core.acknowledge_shared_frame`). Otherwise it renders into a scratch target that nothing reads, and signals nothing. A slow reader therefore drops frames and never stalls the host.
- **Preview targets:** in shared mode, the editor's material previews have shared targets of their own beside the frame target, at most `MAX_PREVIEW_TARGETS` (4), each at most `MAX_PREVIEW_SIZE` (1024) on a side, named `<name>.preview<id>.g<generation>.texture0..2` and `.fence` (see [Rendering](../rendering/materials.md#material-previews)). `gpu_preview_target(id, size)` gives the game a target's texture for the frame, in the render target layout, with its name prefix and generation; it makes the target the first time, and a new generation when the size changes, which waits for the GPU as a resize of the frame target does. The barrier that starts the frame's use goes in at the call, and the frame's end moves the texture to the common layout and signals frame k on the target's fence. A preview has no scratch target: while the reader may still read the texture that frame k would use (k > acknowledged + 2, with `core.acknowledge_preview_frame`), it gives false, and the game draws no preview. `gpu_release_preview_target` releases a target's objects after waiting for the GPU.
- `tools/viewer <name>` opens generation 0 by name and shows the frames in its own window. It has no editor link, so nothing resizes the target and nothing paces it: a viewer that falls more than a frame behind can read a texture that the host is drawing again. `just dev-shared` runs the host and the viewer.

## Future work

- **HDR10 metadata.** The swapchain gets no `DXGI_HDR_METADATA_HDR10`. Setting the display's luminances and the content's would let displays that honour it tone map less. Belongs with the calibration screen in [Rendering](../rendering/layers-and-output.md#hdr-output).
- **Frame pacing beyond vsync.** Standalone presentation paces on vsync, and shared mode on a 60 Hz timer. A frame latency waitable object and a configurable frame cap would give lower latency and a stable cadence on variable-refresh displays.
