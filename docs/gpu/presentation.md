# Presentation

The frame target, output modes for SDR and HDR displays, and shared mode, in which the host renders into shared textures that the editor reads.

- The game renders into a frame target texture that `core` provides. The engine never sees a swapchain.
- The frame target is in the render target layout when the frame starts, and the game must leave it in that layout. Its contents are undefined at the start of each frame.
- `core` reads the window size once at the start of each frame. The frame target has that size, and `window_size` returns it for the whole frame. While the window is minimized, the size is zero and the game renders nothing.
- **Standalone:** `core` copies the frame target to the swapchain and presents with vsync. Vsync paces the frame.
- **Output modes:** `gpu_output` gives the frame's `gpu.Output`: its `Output_Mode`, the frame target's format, which follows from the mode (`output_format`), and the `Display`. `Sdr` is `FRAME_TARGET_FORMAT`, with an sRGB view. `Hdr10` is `RGB10A2_Unorm`, with Rec. 2020 primaries encoded with the PQ curve of SMPTE ST 2084. `Scrgb` is `RGBA16_Float`, linear with Rec. 709 primaries, where 1 is 80 nits. `gpu_request_output` asks for a mode from the next frame on. Its default, `Auto`, is `Hdr10` while the display is in HDR. Set `CINNABAR_OUTPUT` to an `Output_Request` name, such as `CINNABAR_OUTPUT=Scrgb`, and `core` ignores the game's requests and uses that one. Shared mode is always `Sdr`, because the editor reads its textures as sRGB. See [Rendering](../rendering/layers-and-output.md#hdr-output).
- **The display** is the one that shows most of the window: whether the desktop is in HDR on it, its luminances from DXGI, and its SDR white, the brightness that Windows gives SDR content in HDR, from the display configuration. DXGI does not report the SDR white. The D3D12 backend finds the display again every 60 frames, and at once when its factory is no longer current, because the adapters or outputs changed, for example when HDR is turned on or off.
- **A change of mode** waits for the GPU, gives the swapchain's buffers the new format, and sets the swapchain's color space. A mode whose color space the swapchain cannot present falls back to `Sdr`, and is not tried again. The frame target keeps its handle, and its description has the new format, so a pipeline that draws into it needs a version for each format.
- **Editor:** `core` renders into shared textures and signals a shared fence instead (see [Editor](../editor/viewport.md#viewport)). `host --shared <name>` selects this: the window is hidden, and nothing presents. The frame target has the window's size until the editor asks for another one with `core.resize_shared_target`. Each size is a generation of the shared target, and its objects are named `<name>.g<generation>.texture0..2` and `<name>.g<generation>.fence`. The D3D12 backend renders frame k of a generation into texture k % 3 and then signals k on the generation's fence, so a reader that sees fence value v reads texture v % 3. Frames count from 1 in each generation. A resize waits for the GPU, releases the old objects and makes the new ones, and readers keep the old ones alive until they open the new ones. A frame ends with its texture in the common layout, which other processes can use. The textures have the frame target's typed format, because D3D11 cannot open a shared typeless texture, and the editor reads them with D3D11. A high-resolution 60 Hz timer paces the frame. `--adapter <luid>` makes the host use the GPU whose LUID it gives, in hex, because shared objects open only on the adapter that created them.
- **Back-pressure:** while the editor is linked, `core.pace_shared_frames` is on, and the backend renders frame k of a side target into a shared texture only if k is at most the reader's acknowledged frame + 2 (`core.acknowledge_preview_frame` and `core.acknowledge_viewport_frame`); otherwise the target is not given, and the game draws nothing into it. The editor reads the side targets and never the frame target, so nothing acknowledges the frame target's frames: from the third frame after the link it renders into its scratch target, which nothing reads, and signals nothing. A slow reader therefore drops frames and never stalls the host. The pacing timer runs at 60 Hz whatever the targets.
- **Preview targets:** in shared mode, the editor's material previews have shared targets of their own beside the frame target, at most `MAX_PREVIEW_TARGETS` (4), each at most `MAX_PREVIEW_SIZE` (1024) on a side, named `<name>.preview<id>.g<generation>.texture0..2` and `.fence` (see [Rendering](../rendering/materials.md#material-previews)). `gpu_preview_target(id, size)` gives the game a target's texture for the frame, in the render target layout, with its name prefix and generation; it makes the target the first time, and a new generation when the size changes, which waits for the GPU as a resize of the frame target does. The barrier that starts the frame's use goes in at the call, and the frame's end moves the texture to the common layout and signals frame k on the target's fence. A preview has no scratch target: while the reader may still read the texture that frame k would use (k > acknowledged + 2, with `core.acknowledge_preview_frame`), it gives false, and the game draws no preview. `gpu_release_preview_target` releases a target's objects after waiting for the GPU.
- **Viewport targets:** every viewport of the editor, a scene view or the Game view, has a shared target of the same kind, at most `MAX_VIEWPORT_TARGETS` (4), each at most `MAX_VIEWPORT_SIZE` (8192) on a side, as the frame target is, named `<name>.viewport<id>.g<generation>.texture0..2` and `.fence` (see [Editor](../editor/viewport.md#views)). The viewport's number is the target's `id`, with no offset. `gpu_viewport_target(id, size)`, `gpu_release_viewport_target` and `core.acknowledge_viewport_frame` are what the previews' procedures are. The backend keeps both kinds as its side targets, one code path with a name and a largest side for each kind.
- **The frame target with an editor.** The editor shows the viewports' targets and never the frame target: it does not open it, and it does not acknowledge its frames. The frame target's size is only what the game sees as its window, which `core.resize_shared_target` sets from the Game view's size (`Game_Size`), so the game's UI and its camera's aspect follow the Game view. With the back-pressure on and nothing acknowledging, the frame target goes to its scratch target from the third frame after the link and signals nothing. A game that draws every open viewport into its target (see [Rendering](../rendering/frame.md#views)) draws nothing into the frame target, which the frame leaves in the render target layout as it found it; a game with no viewport open draws its own camera into it, as it does without an editor. `tools/viewer`, which has no editor link, reads the frame target as before.
- `tools/viewer <name>` opens generation 0 by name and shows the frames in its own window. It has no editor link, so nothing resizes the target and nothing paces it: a viewer that falls more than a frame behind can read a texture that the host is drawing again. `just dev-shared` runs the host and the viewer.

## Frame capture

The host's screenshots and history ring read the **capture source** back (see [Editor: Capture](../editor/capture.md#capture)): the frame target, which is the start and what a host without an editor reads, or a viewport's target. The capture is the backend's, through `core.request_frame_capture`, `poll_frame_capture` and `release_frame_capture`, and the game has no part in it. A thumbnail is the one capture that the game asks for: `Platform_API.gpu_capture_texture` copies one of its textures in the same way, with a ticket, in `Frame_Capture.ticket`, that says whose it is (see [Thumbnails](../content/daemon-and-operations.md#thumbnails)).

- **A request** between frames takes one of the backend's capture slots, `CAPTURE_SLOTS` (4), each a readback buffer that grows to the frame target's copyable footprint and stays mapped. It has a ticket from the host, as a texture's has one from the game, and `Frame_Capture.source` says which of the two requests made a capture, so the tickets do not collide. One copy of each runs per frame, and a second request in a frame is refused. A request while every slot is held is refused, and so is a frame's request after a minimized frame. A refusal means that the caller asks again next frame.
- **The source.** `core.set_capture_source(viewport)` chooses what the next requests copy: a viewport's number, or nil for the frame target, and `core.capture_source` says which. The host sets it from the editor's `Capture_Source` (a negative number is nil), and sets nil when the editor leaves. A request keeps the source that was set when it was made, and `Frame_Capture.viewport` gives it back, nil for the frame target and for a texture's copy, so a change of source between a request and its frame changes nothing for that copy. A copy of a viewport's target is made in the frame that drew the viewport, from the target as the frame leaves it, in the render target layout: the barriers are those of a texture's copy (render target to copy source and back), recorded before the frame's end moves the target to the common layout for the reader (`end_shared_sides`), so the capture and the editor's reader both see the whole frame. The frame target ends as it does without a capture. The copy has the target's size, which is the viewport's and not the window's, and its format, `FRAME_TARGET_FORMAT`, with the mode `Sdr` and an SDR white of 1. A frame that did not draw the viewport cancels the copy, as a minimized frame does: the viewport is not open, its target is still read by the editor and the game drew nothing, its number is past `MAX_VIEWPORT_TARGETS`, or the backend is not in shared mode. The host takes a cancelled screenshot's request back to wait for a frame, and fails it after `CAPTURE_WAIT_FRAMES` frames, and takes a cancelled ring sample again. The ring keeps the frames of the newest frame's source and size, so a change of either starts it again.
- **A cancel.** A request between frames sees the frame before, so the window can be minimized after a request was taken. A frame that records nothing then copies nothing, and its captures are cancelled. A copy whose readback buffer cannot be made is cancelled too, and only that copy: a frame's failed copy leaves the texture's copy in the same frame alone. A cancelled capture keeps its slot and its ticket, and polling gives it back with `status` `Cancelled` and no pixels, so the caller's request ends and no later answer goes to it. The caller matches every answer by its ticket, never by order (see [Conventions](../overview/conventions.md#state-with-a-lifecycle)).
- **The copy** goes on the frame's final graphics list in `end_frame`, where the frame target would move to the present layout: a barrier to the copy-source layout, `CopyTextureRegion` with the placed footprint, and a barrier to the present layout, which is the common layout that shared mode ends in too. So a capture frame ends as any frame does, and the copy sees every submission, the scratch target of a paced frame included. The slot gets the frame's fence value when the frame is signaled.
- **Polling** gives a cancelled capture first, and otherwise the oldest slot whose fence has passed, as a `gpu.Frame_Capture` with `status` `Ready`: the size, the frame target's format and output mode, the display's SDR white, the row pitch, which D3D12 aligns to 256 bytes, and the backend's mapped bytes, valid until the capture is released. The caller releases every capture that it polls, a cancelled one too. A release is an atomic store, so the host's worker thread releases from where it reads. The zero `Frame_Capture` is `Cancelled`, so a capture that nothing filled in never reads as a copy.
- **Null backend:** a capture is zeroed pixels with the same row alignment, ready at the end of its frame, so the host's tests run without a GPU. Like D3D12, it records nothing in a frame of size zero, which cancels that frame's captures, and its tests can make the next frame copy fail, so a cancel can be tested. It has viewport targets too, plain textures of the target's size that nothing reads and nothing paces, so the capture source can be tested: a copy of a viewport's target is ready when the frame took the target.
