# Render graph

The render graph in `lib/engine/render/graph.odin` is the engine's layer over the command buffers: passes declare their uses, and the graph computes barriers, queue waits, transient and history textures, culling and parallel recording. Read [Command buffers](command-buffers.md) first for the rules it enforces.

The game builds a `render.Graph` every frame in frame memory. Passes declare how they use each resource, and the graph computes the barriers.

- **Passes:** `add_render_pass` or `add_compute_pass`, in execution order. Each pass has a `Pass_Proc` that records its commands through a `Pass_Context`. The graph records the barriers, a timed debug marker with the pass name, so the profiler has each pass's GPU time ([Profiling](../core/profiling.md#gpu-timestamps)), and for a render pass `Begin_Pass` and `End_Pass`. Each pass's recording is also a CPU zone with the pass's name.
- **Pieces:** `pieces = n` splits a pass across `n` jobs (at most `MAX_PASS_PIECES`). The `Pass_Proc` runs once per piece, and `Pass_Context.piece` and `piece_count` tell it which share of the work to record. The first piece records the barriers. A render pass becomes a [split pass](command-buffers.md#split-passes): the graph makes the pieces load and store between each other, and puts each piece's debug marker inside its pass. A compute pass's pieces are plain command buffers.
- **Uses:** `color` and `depth` declare attachments with load and store operations. `read` and `write` declare shader access to textures and buffers. `index_buffer` declares an index buffer, and `indirect_buffer` declares indirect arguments or a count. `import_accel`, `build_accel`, `read_accel` and `build_input` declare acceleration structures, their builds, traces against them, and the geometry and bottom-level structures that a build reads. `add_ray_tracing_pass` adds a pass whose shader accesses synchronize with the ray tracing stage. `copy_source` and `copy_dest` declare the buffers of `cmd_copy_buffer`. A pass can read a resource in several ways, but any other second use of the same resource in one pass is an error.
- **Imported resources:** `import_texture` and `import_buffer` add resources that outlive the frame. An imported texture has a resting use, and the graph returns it to that layout at the end of the frame. The frame target rests as `Color`. A texture created with data rests as `Sampled`.
- **Transient textures:** `create_texture` adds a texture that exists for one frame. The graph adds the usages that its uses need. After culling, the graph gives the transient textures that a live pass uses their GPU textures, and shares one between transient textures whose lifetimes do not overlap:
  - **The rule:** two transient textures of one description, usages included and the label apart, take one texture when the first one's last use comes before the second one's first use. An imported texture or a history texture never shares. Two textures that one pass uses never share either.
  - **Queues:** pass order is not execution order across the two queues (see below). A texture whose last use is on the other queue stays alive until a pass on the second one's queue already waits for that queue, at the second one's first use or before it. So sharing adds no wait, and an async compute pass still runs beside the graphics work. Every queue change in one texture's uses waits, so its last use comes after all of its others.
  - **Barriers:** after a last use on the same queue, the second texture starts in the state that that use left, and its first barrier waits for that use's accesses. After a last use on the other queue, the wait has ordered the accesses, so the second texture starts `Undefined`, as at the start of a frame, and its first barrier discards the contents. A texture's first use is a write in both cases, because sampling a transient texture before a pass writes it is an error.
  - **The cache:** a `Texture_Cache` in `Game_State` keeps the textures between frames, keyed by description, and gives a texture to one graph a frame. Among the textures of one description, it takes the one made with the same label, so a texture keeps its name in a debugger while the frames take their textures in the same order. It destroys a texture after `CACHE_LIFETIME` frames without use. When all `MAX_CACHED_TEXTURES` (400) are in use, it destroys the least recently used one that the frame does not use, so a window resized every frame does not fill it. `MAX_CACHED_TEXTURES` limits the distinct textures of a frame, its views' together. A frame that needs more does not execute.
  - **What it saves:** `Graph.transients` and `Renderer.transients` count the transient textures and the textures that they take, with their memory. At 1080p on the null backend, a frame at Medium has 46 transient textures that take 37, at High 46 that take 39, and at Ultra 48 that take 41. A frame at Ultra that captures a reflection probe's six faces has 139 that take 56, because each face takes the targets of the one before it, and four of the editor's previews of one size take what one does. Textures that one pass reads and writes, as the bloom's up chain and the ambient occlusion's denoiser do, cannot share.
  - **Views:** each [view](../rendering/frame.md#views) of a frame draws in a graph of its own, and its textures are its own too.
- **History textures:** `history_texture` adds a pair of textures that the graph's view keeps between frames (a `History_Set`, in the `View_State` that `begin` is given, or the cache's own if it is given none) and swaps every frame, as temporal passes need: a pass writes `current` in shaders, and reads `previous`, which holds what `current` held in the last frame. Both are imported and rest in the storage layout, with the `Sampled` and `Storage` usages. `previous` is valid only if the history was used in the last frame with the same description and that frame executed, so the first frame, a frame that skipped it, a frame after one that failed, or a new size, which makes the pair again, starts over. Each label is one history, used at most once a frame, and at most `MAX_HISTORY_TEXTURES` exist for a view. A view whose graph does not run in a frame has no valid history in the next, whatever the other views of the frame did. A history that its view did not use for `CACHE_LIFETIME` frames is destroyed when the view's next graph begins, and `view_state_destroy` destroys them at once. `begin` starts a frame in the cache, and `begin_extra` starts the graph of another view in the same frame, without starting another: the first submission of each of its queues waits for the earlier work of the other queue, which the views before it did.
- **Barriers:** a use needs a barrier when it changes the layout, when it follows a write, or when it writes after any access. Reads in the same layout merge without a barrier, so a later write waits for all of them. A transient texture starts `Undefined`, and sampling it before a pass writes it is an error.
- **Culling:** the graph walks the passes backward from the imported resources. A pass is live if it writes a resource that a later live pass reads, if it writes an imported resource, or if `keep_pass` marks it. A write that does not read (for example a clear) makes earlier writers of that resource unnecessary.
- **Handles:** graph handles are valid for one graph. In a `Pass_Proc`, `gpu_texture` and `gpu_buffer` return the `gpu` handles, because transient textures exist only after recording starts.
- **Queues:** `add_compute_pass(..., queue = .Compute)` runs a compute pass on the compute queue. When a pass uses a resource that another queue used last in the frame, the pass waits for that queue. The graph gives the passes their waits after culling and before the transient textures take their textures, so the waits do not depend on sharing, and the resource's state resets as at a frame boundary. Only a layout change still needs a barrier. The compute queue can change a texture only between the undefined, sampled and storage layouts, so when a compute-queue pass needs a texture that a render pass left as a target, the texture's last pass changes its layout after its own work, and the wait orders the change. The ambient occlusion reads the prepass's depth and normals this way.
- **Execution:** `execute` computes all barriers and queue waits in pass order first. Then each piece of each live pass records into its own command buffer on its own job, so `Pass_Proc`s run in parallel. Consecutive live passes on one queue form one `Submission`, and `execute` submits them in pass order. A last command buffer returns imported textures to their resting layouts. When every submission succeeds, `execute` runs the frame's [commits](#commits).

## Commits

State that a frame's GPU work makes changes only after `execute` succeeds, not while the passes are declared or recorded ([Conventions](../overview/conventions.md#state-with-a-lifecycle)). Examples are a built acceleration structure, a baked lookup table, a cleared buffer, a prefiltered cubemap and a written history. `execute` fails when a transient texture cannot be made, when a pass samples a texture before a pass writes it, or when a submission fails. If that state changed while the passes were declared, the next frame would use work that the GPU never did.

- **Commits:** `on_executed(g, commit, data)` adds a `Commit_Proc` and its data to the graph. After it submits the whole frame, `execute` runs the commits in the order they were added. A frame that fails runs none of them, even when some of its submissions reached the GPU. The next frame then does the work again, and a full build or bake again is always safe.
- **What the frame sees:** a feature that needs the new state in the same frame keeps it in its frame data, and its commit copies it. For example, post-processing bakes the lookup table into `Post_Frame.lut`, which the output pass reads. `Post.lut_bake` changes only in the commit.
- **Histories:** `execute` marks each history of its graph's view that the graph used as written. A history's `previous` is valid only after a frame of its view that executed.
- **Lifetime:** `data` is frame memory. The procedures are called in the frame that adds them, so nothing that lasts between frames points into the code, and a [code reload](../overview/hot-reload.md#rules) is safe.
