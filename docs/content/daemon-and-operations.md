# Cook daemon

The daemon keeps the cache current while sources change, owns every `.meta` file, does the editor's asset operations, and serves the cook link.

**In this document:** [Cook daemon](#cook-daemon) · [Saved index](#saved-index) · [Thumbnails](#thumbnails)

## Cook daemon

In development, the cook daemon keeps the cache up to date while the sources change. It is `cook daemon`, in the same executable as the batch commands, so both use the same importers. The editor starts it (see [Editor](../editor/processes-and-projects.md#processes)), and `just watch` runs it without the editor.

`cook daemon --cache <dir> [--definitions <file>] [--dxc <dxc.exe>] [--include <dir>]... [--link <port>] --root <name>=<dir>...`

Without `--dxc`, every shader fails with a problem that says so.

- **Development only:** the daemon cooks the `dev` configuration. Release content comes from the batch commands.
- **The same pass, for what changed:** a daemon pass is the batch commands' pass for every kind (see [Cooking](identity-and-cooking.md#cooking)), but it scans only what changed since the last pass, and carries the rest from the last pass's index (see [Saved index](#saved-index)). A key covers what its asset depends on, so a pass cooks the changed assets and their dependents, and nothing else.
- **Index:** after each pass, the daemon builds an index of the content: every asset with its GUID, root, path, kind, status (current, or failed when it did not cook, an asset that it depends on failed, or no pass reached it; see [Cooking](identity-and-cooking.md#cooking)), import settings, behaviour class, for an action script its name and parameters, dependencies (a script's requires, and the scripts that a scene names), problems, for a sub-asset its parent, for a texture its cooked size, and for a material or an instance its tool texture and hotspots (see [Materials](kinds/materials.md#materials)), and every folder. A problem belongs to the asset whose source or `.meta` file it is in, and the others belong to no asset. The daemon compares the index with the last pass's, and keeps the new one.
- **Removed assets:** when an asset leaves the index, the daemon deletes its blob, so a game that starts later does not load it. A running game keeps the modules that it has loaded. An asset that only shares its GUID with a copy keeps its blob.
- **Orphans:** a `.meta` file without its asset is a warning that belongs to no asset (see [Asset operations](#asset-operations)).
- **Watching:** the daemon watches each root, the definition file's directory and the shader include directories with `ReadDirectoryChangesW`, and keeps the paths that changed. After a change, it waits until 100 ms pass without another, then makes one pass with the paths that changed meanwhile. When Windows drops changes because its buffer filled, or more than 4096 paths changed, the pass looks at everything instead (see [Saved index](#saved-index)). A new definition file makes every script dirty, because it is part of every script's key. A watched directory that goes, as `just clean` deletes the definition file's directory, or whose read fails, is closed and logged once. The watcher checks after each change that the path still names the directory it holds open. While a directory is closed, the wait tries to open it again every 500 ms. When it opens, that counts as a change of everything, so the next pass finds what changed meanwhile.
- **Problems:** an asset that fails is tried again at each pass until it cooks. The daemon logs an asset's problems when they change, and not again at each pass, and a pass that cooks something says how much. A `.meta` file that the daemon writes for a new asset is a change too, so it makes one more pass, which finds nothing to cook.
- **One writer:** the daemon holds the cache's lock while it runs. A second daemon of the same cache stops with an error. A batch cook of another cache, such as a release cook, can run at the same time, and the roots' locks keep the two from giving one asset two GUIDs (see [Cooking](identity-and-cooking.md#cooking)).

### Saved index

The daemon's index also keeps what each pass learnt of each source, so the next pass reads and parses only what changed. It is saved in the cache, so a daemon that starts again checks what changed instead of reading everything. The code is in `tools/cook/scan.odin` and `tools/cook/saved_index.odin`.

- **What it keeps:** the index that the editor gets, and also every file and directory of the roots, the include directories and the definition file, each file with its size and modification time. For every source, a stage's generated texts included, it keeps its `.meta` file's text, its result, and what its cook learnt: its dependencies, the assets that it draws with, its behaviour class, its action and parameters, its sub-assets, its problems, and the files outside the content that its key covers (a model's buffers, and the layers and images that a stage read).
- **The file:** `<cache>/.index`, in the cook link's wire format, written through a temporary file after each pass that changed something. Its header covers the format, the daemon's options (the roots, the includes, the definition file, DXC and the configuration), the cooker executable's size and modification time, and the cache's generation. A file of another header loads nothing, so a rebuilt cooker, other options, or a batch cook of the same cache makes the next pass a full one.
- **Starting again:** the daemon loads the file, and its first pass lists every directory and compares each file's size and modification time with the saved ones. On the sample's 200 assets, it reads no source and takes about 27 ms, where a full pass takes about 230 ms. The editor that links gets the loaded index, and problems that did not change are not logged again.
- **A pass for the paths that changed:** the pass lists only the directories that hold the paths that the watcher reported. A directory that is new is listed with everything in it, and one that went drops everything that was in it. It reads only the assets whose source or `.meta` file changed, or that the saved index does not have. A new `.meta` file that the scan writes is in the next index, so the pass that its change starts reads nothing.
- **What a pass looks at again:** what it read, what went or now shares its GUID, what did not cook at the last pass, what the editor re-imports, and what a file outside the content that its key covers changed in. When files or GUIDs came or went, every asset with problems, as a problem may name what was missing. When a file that is not an asset changed in a root or an include directory, the shaders and the materials, as it may be an include. When the definition file or a `.luaurc` file changed, every script. Then every asset that depends on one of those, directly or not, through its dependencies, the assets that it draws with, or, for a stage's generated texts, its stage. Images with `standalone = false` are looked at in every pass, since whether a set names one is up to every set, but their check reads only their `.meta` files.
- **What it carries:** an asset that the pass does not look at keeps its result, its entry, its thumbnail and its problems from the last pass, and the pass does not read its source. A scene that did not change is not parsed: its warnings and the scripts that it names come from the saved index. A carried prefab is parsed only when a scene that the pass looks at instantiates it, and its problems stay the carried ones. A pass that carries every material keeps the last pass's shading models.
- **Kinds looked at whole:** scripts, and the shading models, material functions, materials and material instances. A pass that looks at one of them looks at all of them. A require names a path, which a new file can change the meaning of, and the type checker reads every module. A material's variants come from the instances that resolve to it, which no dependency says.
- **A full scan:** when Windows drops changes, when a watched directory was closed for a while, and after the editor's asset operations, the pass lists every directory and checks every file's stamp, and every input's of the assets that have them. It reads only what changed. A pass without a saved index reads everything.
- **What it cannot see:** a change that keeps a file's size and modification time, and a change to a file outside the watched directories, such as a stage's layer elsewhere on the disk, until the next full scan. A re-import cooks an asset whatever its stamps say.
- **What a pass costs:** on the sample, a pass after a change to one scene reads one source and takes about 4 ms, and one after a change to a script reads every script and takes about 8 ms. A pass that reads everything takes about 230 ms.

### Asset operations

The daemon is the only program that writes `.meta` files, and it moves every asset with its `.meta` file. The editor asks the daemon for every change to the content roots, except the text of a scene that it saves (see [Editor](../editor/shell-and-panels.md#content-browser)). The operations are in `tools/cook/operations.odin`.

- **The roots' locks:** each operation that changes which `.meta` file is next to which asset (all except create folder and re-import) holds every root's lock while it runs, in the roots' order. A batch cook that scans the roots meanwhile never sees an asset half moved, created or deleted, and gives it no GUID of its own. Each `.meta` file goes through a temporary file and a rename.
- **All or nothing:** an operation checks everything first: the root, the folder, each name, and that no file is in the way. It then fails without changing anything, or does all of it. A move that fails halfway moves back what it moved.
- **Names** are what Windows takes and the scan does not skip: no `<>:"/\|?*`, no name that starts with a dot or ends with a dot or a space, and no device name such as `CON`. An asset's name is without its extension, which the daemon adds.
- **Then a pass:** after the operations that the editor sent, the daemon makes a pass, sends what changed, and then answers each operation. The editor's index therefore has the change when the answer comes. The watcher's events for the operation make one more pass, which finds nothing to cook.
- **Create** makes an asset from a template, with a new `.meta` file: a script that returns a table, a behaviour whose class is named for its file (`door_bell.luau` defines `Door_Bell`), an empty scene, a lit material graph with only its output node, a material function whose one input is linked to its one output, a mesh file of a 1 m box (see [Mesh files](kinds/meshes.md#mesh-files)), a blackboard with no keys, or a decision of a technique, which names no blackboard yet, so it is a problem until its author names one ([Decisions](kinds/decisions.md#the-cook)). A folder's parent must exist.
- **Saving a material** is the editor's, as saving a scene is: the material editor writes the graph's text.
- **Sub-assets** move, rename, duplicate, delete and re-import only with their file, because their GUIDs are in its `.meta` file. The operations take files, never sub-assets: an operation given a sub-asset's GUID fails with a reason that names its file, and the editor disables the file operations while the selection holds a sub-asset. Changing a model's import settings keeps its `mesh.` lines.
- **Move and rename** move the `.meta` file, then the source. They never replace a file, and a rename that changes only the case works. A file moves to another drive too. Folders have no `.meta` files and no GUIDs. A folder renames with everything in it, on its drive.
- **Duplicate** copies the source to `<name>_copy`, or `<name>_copy_2` and on, and gives the copy a new `.meta` file with the same import settings. Its sub-assets get new GUIDs at the next pass, as a new file's do.
- **Delete** sends sources with their `.meta` files, and folders with everything in them, to the Recycle Bin. A root cannot be deleted. The editor finds the assets that use what a delete takes in its index, and shows them in the confirmation.
- **Import settings:** `Set_Import_Settings` takes the new settings of any number of assets, all of them or none. The daemon checks every asset's settings with its importer before it writes anything, writes each `.meta` file through a temporary file, puts back the ones that it wrote when a write fails, and cooks the assets again in one pass, because the settings are part of their keys. A `.meta` file keeps its comments. A setting that the importer does not know stays as the file has it, but the editor cannot add one. **Re-import** cooks assets again with the same settings, also when their keys say that they are up to date.
- **Saving a scene** is the editor's. Save As writes the scene's text where the user picks, and a new scene in a root gets its `.meta` file at the daemon's next pass, as any new file does. A new mesh's and a new weather map's `.meta` files are the editor's to write, with the GUID that the scene names, and the weather map's with `usage = data` and `mips = false`, so the reference resolves at the next pass (see [Editor](../editor/shell-and-panels.md#weather-map)); the daemon owns them from then on.
- **No undo:** asset operations change the project, not the scene, so they are not on the editor's undo stack. The Recycle Bin recovers a deleted asset.
- **Moved modules:** a `require` names a path, so moving or renaming a script breaks the requires of the scripts that require it. The next pass reports each broken require as a problem of the script that has it, with its line.
- **Moves outside the editor:** a source that Explorer or git moves without its `.meta` file gets a new GUID, and the `.meta` file that stays behind is an orphan. The scan reports each orphan as a warning.
- **Directory handles:** the scan reads each directory with `os.read_all_directory_by_path`. Odin's `os.walker` leaves the last directory that it reads open, which would stop the daemon from renaming or deleting that folder.

### Cook link

The editor talks to the daemon through the cook link. It has the editor link's transport (see [Editor](../editor/link.md#editor-link)) and its own messages.

- **One transport:** `lib/engine/wire` has the framing, the wire format and the schema writer, for any union of messages. `lib/engine/editor/link` and `lib/engine/asset/cook_link` each give a union of messages. Neither imports anything from core or engine. The daemon and the host serve with the same `lib/engine/wire/serve`: its accept, reader and writer threads, its outbox and its logger, and which connection is linked (see [Editor](../editor/link.md#editor-link)).
- **The daemon is the server.** It listens on `127.0.0.1` at the port that `--link` gives, and serves one editor at a time.
- **Handshake:** `Hello`, then `Welcome` with the roots, the configuration, the importers, each with its extension and import settings, and the kinds of node of material graphs, then the whole index as an `Asset_Snapshot`, an `Asset_Problems` for each asset that has problems, and the `Shading_Models` with their surface inputs. A `Hello` of another protocol version gets `Refused`, and the editor then stops the daemon and shows the reason. The editor is linked when the snapshot comes, so the index and the session agree. Then the daemon's log goes over the link, as the host's does. If the link closes while the daemon runs, the editor connects again (see [Crash recovery](../editor/processes-and-projects.md#crash-recovery)).
- **After each pass** that changed the index, the daemon sends an `Asset_Delta` and an `Asset_Problems` for each asset whose problems changed, and `Shading_Models` when a shading model changed. It sends `Cook_Finished` after every pass.
- **During a pass** that takes longer than 250 ms, the daemon sends `Cook_Progress` at most every 100 ms and at the end of each step: the step's kind, a stage's name for a stage's step, and the jobs that are done of the total. A step is the assets of a kind, or one stage's meshes and textures, as a stage is most of a large cook. Which counts the messages carry depends on the timing; what the pass cooks does not. A quick pass sends none.
- **An entry has everything that the editor shows,** the import settings, the behaviour class, a sub-asset's parent and name, a material's permutations, a texture's size and a material's tool texture and hotspots included, so the editor never asks for an asset's details. The one image that it opens is a thumbnail, by the path that the entry gives. It finds an asset's dependents in the dependencies of the others.
- **Previews:** `Cook_Preview` gives the text of a material that the editor has not saved. The daemon scans the roots, cooks the text as the material with that GUID, for its default switches only, into the preview area of the cache, `<cache>/dev/preview/<guid>.blob`, and answers with a `Preview_Result` of the same request ID: the first error, or `""`, and the problems with the lines of the text. A preview cooks between passes, writes no generation and changes no index; its problems go in the answer and not to the log. The daemon deletes the preview area when it starts (see [Rendering](../rendering/materials.md#material-previews)).
- **Unsaved animation graphs:** `Cook_Preview` with an animation graph's GUID finds the asset in the daemon's index, without a scan, and answers with the problems that a cook of the text would report, with the file's path and the text's lines. A text without problems goes in the preview area for the editor's [preview](../editor/animation-graph-editor.md#preview), and one with problems leaves the last good one there.
- **Unsaved decisions and blackboards:** `Cook_Preview` with a decision's or a blackboard's GUID finds the asset in the daemon's index, and answers with the problems that a cook of the text would report, with the file's path and the text's lines. A decision's text is checked against its blackboard's source on disk, as the cook reads it, and the cook's blob and the preview area do not change: they have no preview. A GOAP decision's request may carry a plan query, a goal and a start state, which the daemon plans with the runtime's search when the text has no problems, and the answer then carries the plan, or the closest search's ([Decision editor: Plan preview](../editor/decision-editor.md#plan-preview)).
- **Unsaved UI documents:** `Cook_Preview` with a UI document's GUID finds the asset in the daemon's index, and answers with the problems that a cook of the text would report, with the file's path and the text's lines and columns, checking its fonts and images against the index. A text without errors goes in the preview area for the [UI editor's canvas](../editor/ui-editor.md#the-canvas), with the text's FNV-1a hash as its key; warnings do not stop it.
- **Schema:** `cook --emit-link-schema` writes `build/obj/link/cook-schema.json`, and the editor's generator turns it into C# in `Cinnabar.Editor.Link.Cook`, as it does the editor link's schema in `Cinnabar.Editor.Link.Protocol`.

| Group | Messages |
|---|---|
| Session | `Hello`, `Welcome`, `Refused`, `Log` |
| Index | `Asset_Snapshot` with every asset and folder, then `Asset_Delta` with the changed and removed assets and the folders that came and went, and `Shading_Models` |
| Cooking | `Cook_Progress` with a step's kind, a stage's name, and the jobs done and in all, `Asset_Problems` with each problem's file, line, column and text, and `Cook_Finished` with the generation, the counts and the time |
| Previews | `Cook_Preview`, a request answered with a `Preview_Result` of the same request ID; a GOAP decision's `Plan_Query`, answered with a `Plan_Answer` |
| Operations | `Create_Asset`, `Create_Folder`, `Move_Assets`, `Rename_Asset`, `Rename_Folder`, `Duplicate_Assets`, `Delete_Assets`, `Set_Import_Settings`, `Reimport`, each a request answered with an `Operation_Result` of the same request ID: the reason that it failed, or the GUIDs of the assets that it made |

### Thumbnails

The picture that the content browser shows of an asset. The daemon owns which file each asset should have, and removes the others.

- **The file** is `<cache>/thumbnails/<guid>.<key>.png`, outside the content roots, so writing one starts no pass, and the entry's `thumbnail` names it. The key covers what the picture shows: the asset's blob, and the blobs of what it draws with, through what those draw with. A material's are its dependencies. A prefab's are the assets that its flat entities name, since its dependencies are only its scripts and its prefabs. So a texture's new blob gives every material and prefab that uses it a new file, and a reader never sees half of one. `thumbnail_ready` says whether the file is there.
- **Textures and sounds** the daemon makes in its pass, on every core, when the file is missing. A texture's picture comes from its blob's smallest mip that is at least 256 pixels on its longer side, so a stage's textures need no source and no new cook: color keeps its sRGB bytes, a mask is gray, a normal map shows its normals, HDR is tone mapped, and a cube or an array shows its first layer. A sound's is a waveform of each column's lowest and highest sample.
- **Materials, instances, meshes and prefabs** need the renderer, so their entries say that they are not ready, and they show their kinds' icons until the linked host has drawn them. `ThumbnailQueue` in the editor asks for what shows, in Edit mode, one at a time, the last to show first, and the next pass sees the file. A material draws on a sphere, a mesh with the default material, and a prefab as what its cooked flat entities draw, with its materials. A flat mesh turns to face the camera, as a plane that looks away draws nothing. It costs the game nothing but a bake's frames: `lib/engine/editor/thumbnails.odin` loads what it needs for 4 ms a frame, draws into a texture of its own, and asks for a copy once the drawing is [complete](../rendering/materials.md#material-previews), and the host's worker encodes it. A copy that the backend cancels fails the bake with a reason (see [GPU: Frame capture](../gpu/presentation.md#frame-capture)).
- **A part of a prefab**, which the content browser shows when it walks through one, has a picture too, of that entity and what is under it, drawn only while its tile shows. Its file is its prefab's with the part's ID after the key, `<guid>.<key>.<node>.png`. No index entry names it: the editor looks for the file, and the daemon keeps it for as long as it wants its prefab's GUID and key.
- **What keeps a bake from harming the game.** It waits for the cook's generation, or it would record the old picture under the new name. It gives back what only it loaded 2 s after the last bake, and when more than 512 entries are left at the start of one, as the renderer's tables have hard limits. It refuses, with a reason, when any of those tables has fewer than 32 entries left, and when a mesh that it draws is being edited, as the picture would show what is not saved under the name of what is. A bake with nothing that it can load fails too, so no empty picture is kept. Materials are not given back, as a material ref has no release, so after 480 materials or 224 pipelines in one session it refuses until the host starts again.
- **What it cannot do.** A prefab's picture leaves out instanced renderers, so Jungle's is its terrain without its 778 point instancers. A bake that fails is remembered for the session, by the file's name, so what changes the asset tries again: its tile's tooltip says why, and its menu has Regenerate Picture. With no host, or in Play, these tiles show their icons, and the queue waits.
- **What a bake costs:** on the intel sample, a screen of 20 meshes took about 1.5 s and 20 materials at most 3 s, with frames at the usual 16.7 ms. The worst of those had 47 ms of work, where it loads a material's textures, whose blobs are read whole on the main thread, so the 4 ms cannot split them. Jungle's prefab is the worst case: about 6 s, frames of about 25 ms and one of 298 ms, and 5.4 GB more video memory until the release.
- **What it costs:** on the intel sample, making all 359 textures' pictures took about 720 ms, and each pass after that spends time reading each blob's header, once, to find the keys.
