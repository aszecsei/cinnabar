# Identity and cooking

GUIDs and `.meta` files, and what every cook has in common: shared schemas, cache keys, the single scan, the generation counter, the locks and problems. Each asset kind's own cook is in [kinds](README.md#documents).

**In this document:** [Identity](#identity) · [Cooking](#cooking)

## Identity

Every source asset has a GUID, stored in a `.meta` sidecar file next to it with its import settings. The cooker assigns a GUID the first time it sees an asset. Renames and moves keep the GUID as long as the `.meta` file moves too, and the editor makes sure it does. Content refers to other content only by GUID.

- A GUID is 128 random bits, written as 32 hex digits. Engine content (such as the script prelude) has fixed GUIDs in committed `.meta` files.
- A `.meta` file has lines of `key = value`, and `#` comments. `guid` is required. The other keys are import settings. When the cooker finds an asset without a `.meta` file, it writes one. Commit it with the asset. The cooker writes each `.meta` file to a temporary file and renames it, so a scan or the editor never reads a partial one.
- **Sub-assets:** one source file can make several assets, such as the meshes of a glTF file. Each sub-asset has its own GUID and its own blob, and loads like any other asset. Its GUID is in its file's `.meta` file, on a line `<kind>.<name> = <guid>`, such as `mesh.Door_Frame = 3f9c...`. The cooker writes the line when it first makes the sub-asset, and finds it again by kind and name, so a re-import keeps every reference. The file itself is the parent, and has a GUID of its own but no blob when it makes only sub-assets.
- **A renamed sub-asset** (a mesh renamed in the modelling tool) gets a new GUID, with a warning that names the old one. The old line stays in the `.meta` file, as a warning, until the asset is re-imported, so a rename back in the modelling tool restores it.
- Two assets with the same GUID, of any kinds, are a cook error, and neither cooks. This happens when an asset is copied with its `.meta` file. Delete the copy's `.meta` file to give it a new GUID.
- Each game has one content root, `samples/<game>/content/`. Engine content is in `lib/engine/content/`. The cooker takes each root with a name, such as `--root game=samples/mygame/content`, and an asset's source path is the root's name and its path in the root, such as `game/scripts/hello.luau`.
- At runtime, a loaded asset is a generational handle in the asset runtime's table. Persistent state holds handles or GUIDs, never pointers into blobs (see [Hot reload](../overview/hot-reload.md#rules)).

## Cooking

- **Shared schemas:** `tools/cook` imports the same asset-type package from `lib/engine` that the runtime uses, `lib/engine/asset/format`, so their struct layouts cannot diverge. That package imports nothing from `lib/core`. Each asset type's version comes from its layout hash, so changing a type invalidates its cache entries.
- **Incremental cooking:** a cache key is a hash of the source files, the import settings and the cooker version.
- **Every kind at once:** `cook all` cooks every kind in one pass, with one scan, as `cinnabar.exe` and `just release` do. With `--prune`, it then deletes each blob in the cache whose GUID no asset in the roots has, as an asset's or a sub-asset's, so a package step after it packs only the content's. A release cache goes through it, as nothing else deletes the blobs of assets that left the content there; the daemon does that for the development cache (see [Cook daemon](daemon-and-operations.md#cook-daemon)).
- **One scan:** every command that cooks scripts or scenes scans the roots once for every kind of asset, and gives each new asset its `.meta` file, whatever kind it cooks. Then it cooks each asset of its kinds whose key changed. The cook daemon scans only what changed since its last pass (see [Saved index](daemon-and-operations.md#saved-index)).
- **Each asset's result:** the pass of an asset's kind settles what came of it, once: current (its blob was up to date, or it has nothing to cook), cooked, failed, or blocked (an asset that it depends on failed, such as a script that it requires or its material's shading model). An asset starts pending, so a pass that stops early, as when it cannot make the cache's directory, fails each asset of its kind that it has not settled, and the index reports one that no pass reached as failed, not current. A shading model settles only after every one has parsed, since two with one name, as a game's `lit.shading` beside the engine's, both fail. When the definition file does not load, each script whose key changed fails, not only the first.
- **The cache's generation:** after a cook writes blobs, it adds one to the counter in `<cache>/<config>/.generation` (see [Loading](blobs-and-loading.md#loading)).
- **One cook for each cache:** a cook holds `<cache>/.cook.lock` while it runs, so two cooks never write one cache's blobs, index and generation file at once. Windows deletes the lock when the cook exits, also when it crashes. A dev batch cook that finds the lock held leaves the cache to the cook daemon, which keeps it up to date, so `just build` works while the editor is open. Any other cook of the same cache stops with an error.
- **One GUID for each asset:** the `.meta` files are in the roots, which cooks of different caches share, such as the daemon and a release cook. So a cook holds `<root>/.cook.lock` while it writes a `.meta` file in that root: when it gives a new asset its GUID, and when it adds a sub-asset's line. The scan skips the lock, as its name starts with a dot. A cook that finds an asset without a `.meta` file takes the lock and looks again, and uses the `.meta` file that another cook wrote meanwhile. If the asset itself is gone, as when the daemon moved it, the scan leaves it out. A cook that adds a sub-asset's line reads the `.meta` file again under the lock, so it keeps another cook's sub-asset GUIDs and the daemon's new import settings. Each of the daemon's asset operations holds every root's lock (see [Asset operations](daemon-and-operations.md#asset-operations)). A cook holds a root's lock for milliseconds, so another cook waits for it, for up to 10 s.
- **Problems:** each error and warning names its file (the asset's source or `.meta` file, or another file such as the definition file), and its line and column when it has them. A batch cook logs each one as `cook: <file>:<line>:<column>: <text>`.
- **Kinds:** scripts, scenes, shaders, textures, models, mesh files, stages, materials, effects, animation graphs, sounds, fonts, UI documents, sprite sheets, blackboards and decisions. Each kind has an importer: its extensions, its import settings and its cook (see the sections below). Meshes, skins, animations, prefabs and instance sets also come as sub-assets of models and stages, which have no importer of their own, and a font's atlas is a texture sub-asset of it, as is the atlas of a sprite sheet that packs images.
- **Slow kinds use every core.** A texture can take seconds, so block compression spreads each mip's rows of blocks over the CPU's threads. A 2048×2048 color texture with its mips cooks in about 1 s for development and 3 s for release. The loose textures, and a stage's meshes and textures, also cook at once, one job for each on a thread for each of the CPU's (`parallel_for`), at most one thread for each 2 GiB of memory, since a 4096×4096 texture takes about 1 GB as it cooks. Decoding and mip filtering run one to a thread, so this is what spreads them. Each job reports into its own scratch, and the pass takes the jobs' counts and problems in the assets' order after, so a cook's blobs and messages are the same as one at a time. Each job also counts itself done for the daemon's progress (see [Cook link](daemon-and-operations.md#cook-link)), which changes nothing that the cook writes. Intel's Sponza stage cooks in 66 s, from 163 s, on 32 threads, at most 20 GB.
- **Third-party code** for the importers is in `vendor/`, built with CMake into `build/` like Luau, and linked into `tools/cook` only: Compressonator's `CMP_Core` for block compression, meshoptimizer for meshes, libogg and libvorbis to encode sounds, msdfgen's core for fonts' distance fields, and Recast for navmeshes. Odin's `vendor:stb/image`, `vendor:cgltf`, `vendor:miniaudio` and `vendor:stb/truetype` read the source files. The runtime links none of them. **Three codecs are the exception, as what is compressed must be decoded where it is used:** the runtime links LZ4 (`lib/core/lz4`), which the cooker compresses a mesh's pages with (see [Meshes: Pages](kinds/meshes.md#pages)), libopus, which the cooker also encodes with, and Odin's `vendor:stb/vorbis`, for both the host's mixer and the game's load of a sound (see [Audio](kinds/audio.md#audio)). The cooker must not link `stb_vorbis` as well, as `vendor:miniaudio` already holds a copy, so its tests read Vorbis through miniaudio.
- **Compressonator** is a submodule pinned to a release, but its repository is over 700 MB, so `vendor/compressonator` is a blobless clone that checks out only `cmp_core`, `license` and `applications/_libs/cmp_math`. `.gitmodules` marks it `update = none`, so `git submodule update` never checks out the rest, and `just install-compressonator` makes the sparse clone at the pinned commit. `just update-compressonator <tag>` moves the pin. `tools/cook/compressonator` builds `CMP_Core` with its own CMake project, and `cn_compress.cpp` gives the cooker a C API that compresses a whole mip, because `CMP_Core`'s API is C++ and compresses one block at a time.

The kinds below are in the order a game meets them: scripts and scenes are what gameplay is made of, and shaders, textures, meshes and materials are what the renderer draws.
